## Hard constraints for the submitted bot (`bot/`)

Source: `docs/rules/SUMMARY.md`. *(prov.)* = provisional, may change before the deadline.

- **Python 3.11 only.** Stdlib + NumPy + SciPy (SciPy only if truly needed, imported lazily).
  No other imports in `bot/`; a test enforces this. No installs at runtime.
- **Resources:** 1 vCPU, 1 GB RAM *(prov.)*, no network, read-only filesystem.
- **A bot may not read or write files, open sockets, or start other processes.** No
  `multiprocessing`/`subprocess` in `bot/`. Config, spec and tables are embedded in source:
  `bot/embedded.py` is generated by `tools/embed_data.py` from `bot/config/*.json`,
  `variant/active.json` and `data/<variant>/` (`.venv/bin/python -m tools.embed_data`; a test
  fails when it is stale). A static scan (`tools/sandbox_scan.py`) and an audit-hook run guard it.
- **I/O:** JSON lines over stdin/stdout (`docs/rules/protocol.pdf`). **stdout = protocol
  messages only**, flushed after every one. Debug output goes to **stderr** (64 KB per match cap,
  never parsed).
- **Time bank** *(prov.)*: 60 s per 400-hand Stage 1 match; 150 s per ~1000-hand Stage 2
  match. It is charged from when a request is sent until the full reply arrives, for **both
  action and discard** requests. Read `total_hands` and `time_bank_ms` from `init` and
  `time_left_ms` from each request; never hardcode. Assume the server is ~2× slower than a laptop.
  Pacing (`bot/timing.py`): ~5.5 decisions of ours per hand (the discard counts), safety 5.5 (was 4.5 until Phase E), budgets
  capped at 1.2× the opening pace, hard limit ≤ 0.3 × the reply limit (1.5 s). Real use is ~22–24 %
  of the bank; projected at 2× slower it must stay ≤ 50 % (`lab.timing_bench`, `tests/test_timing_slow.py`).
- **Any single reply within 5 s** *(prov.)*. **Wall-clock kill:** 180 s per Stage 1 match,
  450 s per Stage 2 match *(prov.)*.
- **Start-up:** 5 s from launch to ready for `init`, not charged to the bank.
- **Forfeit** (crash, exhausted bank, a reply over 5 s, or the wall-clock kill): a loss, and the
  opponent's result is set to +C.
- Randomness is allowed. No state is kept between matches (fresh process per match).
- **Submission:** `python3.11 bot.py`; a single `bot.py`, or a `.zip` with `bot.py` at the top
  level, ≤ 5 MB including any tables. Build + verify: `.venv/bin/python -m tools.package_submission --zip --stage2`
  (writes `dist/submission.zip`; all checks run on the unpacked zip).
- **Scoring:** every deal is played twice with seats swapped (the bot isn't told which deals are pairs).
  The match is won by the bot with more net chips: win 1, draw 0.5, loss 0. Tie-break: capped chips
  per hand Σ clip(Δm, −C, C) / Σ Hm, with C = 400 (Stage 1) and 1000 (Stage 2) *(prov.)*. We
  optimise for *winning matches*, not maximum chips.
- **Tournament:** Stage 1 is Swiss, 6 rounds (7–8 if >~1000 teams), 400 hands per match
  (a round robin if <~64 bots, skipped if ≤ 32). Stage 2: the top 32 play a round robin of ~1000 hands
  per match, scores reset; Stage 2 alone decides the prizes.
- **Code review / originality:** prize-winning code is reviewed and similarity-checked.
  Copying from other teams or public bot repos is prohibited. *(User decision 2026-11-04: the `Opps/`
  bots were written by us, so reading them and reusing their ideas or code in `bot/` is allowed; the
  old "ideas only" rule is lifted. Still never copy other teams' or public bot code.)* Exploiting the engine or evaluation system is prohibited and must be
  reported; exploiting other bots' play is fine.

## Architecture rules

- A variant is a JSON spec (`variant/spec.py`; presets in `variant/catalog/`; the bot plays
  `variant/active.json`, embedded into `bot/embedded.py`; the lab overrides it with the spec JSON
  *text* in `$POKERBOT_VARIANT_JSON`). It compiles into a **hand program** of step
  plugins (`bot/game/compile.py`). The legacy `GameConfig` is gone (2026-10-29): specs only;
  `holdem_rules()` is the default where no variant is given.
  Never hardcode Hold'em numbers (2 hole cards, 5 board cards, 3/1/1).
- `bot/game/` = the rules, pure and submit-safe (state, steps, payoffs, scoring). The lab
  engine and the bot's simulator (`bot/sim/`) run the same code. Information only flows
  through `state.emit(..., visible=...)`; hidden-information correctness is tested.
  What a player receives for each event is `bot/game/observation.messages_for` (engine and
  replay both use it).
- Shared modules a brain builds on (terms in `GLOSSARY.md`): `bot/situation.py` (per decision:
  reconstruction, equity, special-step policy, endgame lock), `bot/opponent.py` (stats +
  inference + trust, `range_weights`), `bot/artifacts.py` (embedded precomputed data),
  `bot/abstraction.py` (the CFR abstraction, shared with the lab trainer). New brains are
  policies over these; don't subclass Tier 1 just to get them.
- Wire formats live only in `bot/protocol.py` (neutral messages) and `bot/protocols/`
  (one adapter per format). Brains see only neutral objects (state, legal actions, budget).
- `lab/` is offline tooling, never submitted; it may use anything in the dev venv.
- Safety, three layers: (1) brain in try/except → Tier 0 on error; (2) every action
  validated + clamped before sending; (3) hard deadline or brain error → one retry of the brain at budget 0 (RC, `bot/main.py` `retry_cheap`), then Tier 0; emergency mode → Tier 0.
  The main loop never lets an exception escape (clean exit on EOF only).
- macOS uses `spawn` for multiprocessing: `if __name__ == "__main__":` guards and
  picklable top-level worker functions.

### CLAUDE.md: Pokerbots bot

2-person team. Python bot. Deadline: Nov 15, 23:59 IST.

#### Hard constraints (from the organisers)
- Python 3.11. Standard library, NumPy, and SciPy only. No pip at runtime.
- 1 vCPU, 1 GB RAM, read-only filesystem, no network.
- Time bank: cumulative per match, about 60 s for 400 hands (roughly 0.15 s per hand on average), with a hard wall-clock kill. A crash or an exhausted bank forfeits the match.
- The bot talks to the engine over a fixed stdin/stdout protocol. Read the starter code for the exact format. (Now: `docs/rules/protocol.pdf`.)
- All matches use duplicate deals: every deal is played twice with seats swapped.
- Stage 1: Swiss, 6 rounds of about 200 duplicate deals (400 hands). Win 1, draw 0.5, loss 0.
- Stage 2: top 32, round-robin, about 500 duplicate deals each, scores reset.
- Tie-breaker: capped chips per hand. Check the rules for the cap before optimising for margin.

#### Approach
1. **Strength first.** Build the strongest bot you can inside the hard constraints. Do not weaken the design for speed worries that tuning can fix later.
2. **Some limits are design limits, not tuning limits.** Memory (1 GB), the time bank, and the library list decide which algorithms are even possible, so they apply from day one. At about 0.15 s per hand on one core, heavy search or solving cannot run online. Train and precompute offline, ship compact tables in the repo (the filesystem is read-only, so the bot cannot write or cache anything), and keep online decisions cheap lookups plus light computation. Any ML model must run in NumPy only.
3. **Spend the time bank on purpose.** The bot tracks its own remaining time and switches to a cheap fallback policy when the bank runs low. Never run out. Measure per-hand time and peak memory; never guess either.
4. **Never crash.** Wrap the decision path so any exception returns a safe legal action. A crash forfeits the match.
5. **Then fit.** Once the strong version works, profile and cut it to the limits. Trade strength for speed only where measurements say so, and state what was traded.
6. **Read the rules yourself.** On the first session, read the rules and starter code in the repo, fill in "Open questions" and "Commands" below from them, and ask me only for what you cannot find. Do not guess.
