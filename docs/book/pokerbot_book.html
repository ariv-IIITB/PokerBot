                  Chapter 1 — The Concepts, from the Ground Up

                  This chapter is a self-contained course. Each section only uses earlier ones. Where you already know the material (linear algebra, basic probability, Nash equilibrium) the pace is brisk; from extensive-form games onward it slows down and proves things.

                  1.0 How to read this book

                  There are three kinds of boxes. Key idea boxes state the one thing to remember from a section. Pitfall boxes describe a mistake that has actually cost someone time, often in this very project. In Chapter 2 boxes point forward to where the idea is used in the repository; you can ignore them on a first read.

                  Words in bold colour are being defined at that spot; every such word is in the glossary at the end. A dotted underline, like equity, links to its glossary entry. Each section ends with a few exercises; answers are in the answer key after the glossary. The exercises are short on purpose: if one takes you more than ten minutes, re-read the section instead.

                  Notation: P(A) is a probability, E[X] an expectation, Var(X) a variance, Σ a sum, ‖x‖ a norm, [x]+ = max(x, 0) the positive part. Chip amounts are integers; "chips/hand" means average chips won per hand.

                  1.1 Tools: the terminal, git, Python and tests

                  A competition bot is software first and poker second. Nearly every disaster in this kind of project is a software disaster: a crash that forfeits a match, a branch that never got merged, a test that silently stopped running. So we start with the tools.

                  1.1.1 The terminal in five minutes

                  A shell (here bash) is a program that reads a line of text, runs the command it names, and prints what the command writes. Every command has three standard streams: standard input (stdin, what it reads), standard output (stdout, what it prints) and standard error (stderr, where diagnostics go). They are just byte streams. a | b feeds the stdout of a into the stdin of b; > file sends stdout to a file; 2> file sends stderr.

                  Why this matters: our bot is a command. The tournament engine starts python3.11 bot.py, writes one JSON message per line to its stdin, and reads one JSON reply per line from its stdout. Anything else printed to stdout (a stray debugging print) corrupts the conversation. Debug text must go to stderr.

                  Every command also returns an exit code: 0 means success, anything else failure. Scripts chain commands with && ("run the next only if this succeeded"). Paths are either absolute (/home/user/PokerBot/bot/main.py) or relative to the current directory (bot/main.py).

                  1.1.2 Git from first principles

                  Git is easiest to understand from its data model, not from its commands. Once you see what it stores, every command is obvious.

                  Snapshots and hashes

                  Git stores snapshots of your whole project, not diffs. A snapshot is built from three kinds of objects:

                  • a blob: the bytes of one file;
                  • a tree: a directory listing, mapping names to blobs and sub-trees;
                  • a commit: a pointer to one root tree, plus the author, a message, and the IDs of its parent commit(s).

                  Every object is named by a hash: a 40-hex-digit fingerprint (SHA-1) computed from its contents. Change one byte anywhere and the blob's hash changes, so the tree's hash changes, so the commit's hash changes. A commit hash like 3f61900… therefore identifies an exact state of every file and the entire history behind it. We usually abbreviate hashes to 7 characters.

                  Because a commit names its parents, commits form a directed acyclic graph (DAG): arrows point from child to parent, and you can never go in a circle.

                  Branches are just labels

                  A branch is nothing but a movable name that points at one commit. main is a branch like any other; it is special only by convention. When you commit while "on" a branch, git creates the new commit with the current one as parent and moves the label forward. HEAD is the name of "where you are now": usually it points at a branch, which points at a commit.

                  Creating a branch costs nothing (a 41-byte file). This is why the project creates a branch for every phase and merges it into main afterwards.

                  The three places a file lives

                  At any moment a file exists in up to three versions:

                  1. the working tree: the file on disk that your editor changes;
                  2. the index (also called the staging area): the snapshot that the next commit will record;
                  3. the last commit (HEAD).

                  git add f copies the working-tree version of f into the index. git commit turns the index into a new commit. git status shows the differences between the three: "changes not staged" are working tree vs index; "changes to be committed" are index vs HEAD; "untracked" files are on disk but were never added. git diff shows working tree vs index, git diff --cached index vs HEAD.

                  A .gitignore file lists patterns git should never offer to add (build outputs, caches). Rules are read top to bottom and a later rule wins; !pattern re-includes something an earlier rule excluded. One subtlety: git cannot re-include a file inside a directory that is itself excluded, because it never looks inside that directory. That is why "ignore everything in data/ except one folder" must be written data/* then !data/discard_holdem/, not data/.

                  Merging

                  To combine two lines of work, git finds their merge base: the most recent commit that is an ancestor of both (C in Figure 1.1). Then there are two cases.

                  • Fast-forward: if one branch is an ancestor of the other (nothing happened on main since you branched), "merging" just moves the label forward. No new commit, nothing can conflict.
                  • Three-way merge: otherwise git compares each file in three versions (base, ours, theirs). A region changed on only one side takes that side's change. A region changed differently on both sides is a merge conflict: git writes both versions into the file between <<<<<<<, ======= and >>>>>>> markers and stops. You edit the file to the correct result, git add it, and commit. The result is a merge commit with two parents (M).

                  A conflict is not an error; it is git refusing to guess. The dangerous case is the opposite: two sides that change different lines but whose meanings clash. Git merges those silently, and only tests catch the problem.

                  Rebase

                  Rebase is the alternative to merging: it takes your commits E, F and re-applies them one by one on top of D, producing new commits E′, F′ with new hashes, as if you had started from D. History becomes a straight line. The cost: the old commits E, F are replaced. If anyone else already has E and F, their history and yours now disagree. The rule is therefore: never rebase commits that someone else may have. And never force-push (overwrite a remote branch with history that does not contain it), because that deletes other people's commits from the shared copy.

                  Remotes: fetch, push, pull

                  A remote is another copy of the repository, usually on GitHub, conventionally named origin. Git keeps remote-tracking branches such as origin/main: your local record of where main was on the remote the last time you looked.

                  • git fetch downloads new commits and updates origin/*. It never changes your own branches.
                  • git push origin X uploads your commits and asks the remote to move its X label. The remote refuses unless this is a fast-forward (unless forced).
                  • git pull is fetch followed by a merge (or rebase) into your current branch.
                  Pitfall

                  Your local main and origin/main are different things. If you never run git fetch, you are comparing against a stale picture. In this project an assistant once reported "branch X is missing from main" because it compared against an old local main; another session had merged X an hour earlier. Always fetch first, and compare against origin/main.

                  Pull requests and CI

                  A pull request (PR) is a GitHub page that proposes merging one branch into another, shows the diff, collects review comments, and records automated check results. Continuous integration (CI) is the automation: on every push, a fresh machine checks out the code, installs dependencies and runs the test suite. A red mark on a commit means a test failed. CI's value is that it runs on a clean machine: if your code only works because of a file that exists on your laptop but was never committed, CI fails where you would have succeeded.

                  Key idea

                  A commit is an immutable snapshot named by its hash; a branch is a movable label; merging finds the merge base and combines changes; CI runs the tests on a clean checkout. Fetch before you compare.

                  1.1.3 Python projects: interpreters, environments, imports

                  The competition runs Python 3.11 with only the standard library, NumPy and SciPy. Different Python versions differ in small ways, so we test on exactly 3.11.

                  A virtual environment (venv) is a folder (.venv/) containing its own Python interpreter link and its own installed packages, so one project's packages never interfere with another's. Dependencies are listed with exact versions in a requirements file (numpy==2.3.4). Pinning versions makes every machine install the same thing, so a result on one machine reproduces on another.

                  A module is one .py file; a package is a folder of modules with an __init__.py. python -m bot.main runs the module bot/main.py as a program with the repository root on the import path. Imports are resolved by searching that path, which is why an innocent file named json.py in the wrong folder can shadow the real json library.

                  1.1.4 Tests, seeds and determinism

                  A unit test is a small function that runs some code and asserts a result. pytest finds files named test_*.py, runs every function named test_*, and reports which assertions failed. Useful features:

                  • markers: @pytest.mark.slow tags a test; -m "not slow" skips the tagged ones;
                  • parametrisation: @pytest.mark.parametrize("hands", [400, 1000]) runs one test body for several inputs;
                  • -n auto (the pytest-xdist plugin) runs tests in parallel worker processes, one per CPU core.

                  Tests must be deterministic: same code, same result, every run. Card games are random, so we fix the seed of every random number generator (RNG). A pseudo-random generator is a deterministic function: given the same seed it produces the same sequence. numpy.random.default_rng(12345) always deals the same cards.

                  One trap: code that uses time to decide how much to compute ("sample until 50 ms have passed") is not deterministic, because a busy machine samples less. Such tests become flaky: they pass alone and fail under load. The fix is to bound work by a count ("200 samples") in tests.

                  Good tests check behaviour through a public interface ("a broken input line still gets a legal reply"), not internals ("function X was called twice"). And their expected values come from an independent source: a hand-computed number, a rule in the rulebook, never a recomputation of what the code does (a tautological test can never fail).

                  Test-driven development (TDD) is the discipline "write the failing test first, then the minimal code that makes it pass". The failing step ("red") proves the test can detect the bug; without it you do not know whether the test tests anything.

                  1.1.5 NumPy and vectorisation

                  Pure Python executes one bytecode instruction at a time, roughly 10–100 nanoseconds each. A loop over a million elements therefore takes tens of milliseconds even if each step is trivial. NumPy stores numbers in contiguous typed arrays and runs whole-array operations in compiled C, often using SIMD instructions. a + b on two million-element arrays takes about a millisecond: 20–100× faster than the loop.

                  Vectorisation means rewriting "for each element do f" as array operations. The core tools: elementwise arithmetic, broadcasting (an array of shape (n, 1) combined with one of shape (1, m) behaves like (n, m)), reductions (sum, max along an axis), fancy indexing (a[idx] with an integer array), and matrix products (A @ x), which call highly optimised BLAS routines. Matrix-vector products are the reason CFR can be made fast (Section 1.7.6).

                  A GPU is the extreme form of the same idea: thousands of simple cores running the same operation on different data. It pays off when the work is large, regular arrays (matrix products over tens of thousands of elements). Small, branchy, irregular work (walking a game tree node by node) runs worse on a GPU than on a CPU.

                  1.1.6 Processes, time limits and failure

                  The engine runs our bot as a separate process and talks to it over pipes. Three facts follow:

                  • If our process crashes, the engine sees end-of-file on our stdout and we forfeit the match.
                  • If we take too long to reply, we also forfeit. The engine measures wall-clock time from sending a request until our reply line arrives.
                  • If the engine closes our stdin, reading returns end-of-file (an empty string); a well-behaved bot exits cleanly. If it closes our stdout, writing raises BrokenPipeError.

                  Unix offers a signal-based alarm: signal.setitimer asks the operating system to interrupt the process after t seconds, which raises an exception inside whatever code is running. This is a hard deadline for a computation that might run too long. A time bank is a budget of seconds for a whole match; each decision draws from it. Budgeting it is a small control problem: spend too little and play worse, spend too much and run out.

                  1. You run git add a.py, then edit a.py again, then git commit. Which version of a.py is in the commit?
                  2. main is at D. You branch at D, make commit G, and nobody touches main. What does merging your branch into main do?
                  3. Why can't data/ followed by !data/keep/ in .gitignore re-include data/keep/?
                  4. A test asserts compute(x) == compute(x). What is wrong with it?
                  5. Your bot prints "thinking..." with print() before each reply. What happens in a match?

                  1.2 Probability and statistics: a working refresher

                  You know this material; the point of this section is to fix notation and to show the handful of results we lean on constantly: standard errors, confidence intervals, sample sizes and the multiple-testing trap.

                  1.2.1 The basics in one page

                  A random variable X assigns a number to each outcome (the chips we win in one hand). Its expectation E[X] = Σx x·P(X=x) is the long-run average. Expectation is linear: E[aX+bY] = aE[X]+bE[Y] always, whether or not X and Y are independent. This one fact justifies most of poker arithmetic: the value of a decision is the probability-weighted sum of the values of its outcomes.

                  The variance Var(X) = E[(X−EX)2] measures spread; its square root is the standard deviation σ. For two variables, Var(X+Y) = Var X + Var Y + 2 Cov(X,Y), where the covariance Cov(X,Y) = E[(X−EX)(Y−EY)] is zero for independent variables and negative when one tends to be high when the other is low. Keep this formula in mind: Section 1.3 exploits the negative-covariance case.

                  Conditional probability: P(A|B) = P(A∩B)/P(B). Bayes' rule turns it around:

                  P(H | D) = P(D | H) · P(H) / P(D)

                  Read it as "posterior ∝ likelihood × prior". H is a hypothesis ("the opponent is a calling station", "the opponent holds a flush"); D is the data we observed (their actions). The prior P(H) is what we believed before; the likelihood P(D|H) is how probable the data would be if H were true; the posterior is the updated belief. In odds form, which is easier to use in your head:

                  posterior odds of H1 vs H0 = (likelihood ratio) × (prior odds) = [P(D|H1)/P(D|H0)] × [P(H1)/P(H0)]

                  With independent observations D = (d1, …, dn) the likelihood ratios multiply, so the logarithms add. The log-likelihood ratio (LLR) is the natural "evidence counter": every observation adds log[P(dt|H1)/P(dt|H0)].

                  1.2.2 Averages, the CLT and standard errors

                  Let X1, …, Xn be independent draws with mean μ and standard deviation σ (the chips of n hands). Their average X̄ has mean μ and standard deviation

                  SE = σ / √n

                  called the standard error of the mean. The law of large numbers says X̄ → μ; the central limit theorem (CLT) says more: for large n, X̄ is approximately normal, X̄ ≈ 𝒩(μ, σ2/n). So the interval X̄ ± 1.96·SE contains μ about 95% of the time: a 95% confidence interval. "± 2 SE" is the usual shorthand.

                  Poker is noisy. A single heads-up hand with 200-chip stacks and 1/2 blinds can swing 200 chips, and its standard deviation is of the order of 50 chips. (That figure is not a law; it is what the standard errors reported in Chapter 2 imply for these bots.) Plug in:

                  handsSE of chips/hand (σ = 50)
                  400 (one Stage-1 match)2.5
                  4,0000.79
                  40,000 (50 duplicate pairs of 400)0.25
                  400,0000.079

                  To halve the error you need four times the data. Typical edges between decent bots are 0.5–2 chips/hand, so one match tells you almost nothing about which bot is better; you need tens of thousands of hands.

                  1.2.3 How many samples? Tests, power and the multiple-testing trap

                  To claim "A beats B" we usually require the observed edge to exceed 2 SE. Two errors are possible. A false positive (type I) declares an improvement that is pure noise; with a one-sided 2-SE rule its probability is about 2.3% per test. A false negative (type II) misses a real improvement. The power of a test is 1 − P(false negative). To detect a true edge δ with a one-sided 2-SE threshold and 80% power, you need roughly

                  n ≈ ((2 + 0.84) · σ / δ)2

                  With σ = 50 and δ = 1 chip/hand: n ≈ (142)2 ≈ 20,000 hands. With δ = 0.5: 80,000 hands. These numbers set the budget of any tuning loop (Section 1.10).

                  Pitfall: multiple comparisons

                  Try 20 random changes that do nothing, and test each at "2 SE". Each passes by luck with probability ≈ 2.3%, so the chance that at least one passes is 1 − 0.97720 ≈ 37%. The change you keep is then the luckiest, and its measured gain is biased upward: the winner's curse. The cures: re-test the winner on fresh seeds (the gain usually shrinks), raise the threshold when many variants are tried (the Bonferroni correction divides the error rate by the number of tests), and keep a held-out set (Section 1.10.5).

                  Exercises 1.2

                  1. A bot's measured edge is +0.6 ± 0.25 chips/hand (± 1 SE). Is it significant at 2 SE? What is the 95% confidence interval?
                  2. You want SE = 0.1 chips/hand with σ = 50. How many hands?
                  3. A test of "opponent is a maniac" has likelihood ratio 4 per observation in favour, and prior odds 1:9. What are the posterior odds after two independent observations?
                  4. You test 8 parameter changes; one passes at 2 SE. Roughly how likely was at least one false pass if none of them helps?

                  1.3 Monte Carlo and variance reduction

                  1.3.1 Monte Carlo estimation

                  Many quantities in poker are expectations we cannot compute in closed form, such as "the probability my hand wins at showdown against a random hand". Monte Carlo estimation replaces the expectation by an average over random samples: deal the unknown cards at random n times, count wins. The estimate is unbiased and its error is the standard error of a proportion, √(p(1−p)/n): at p = 0.5 and n = 1,000, about ±1.6 percentage points (1 SE). Error falls only as 1/√n: the same law as Section 1.2.2.

                  Importance sampling draws samples from a convenient distribution q instead of the true p, and corrects each sample by the weight p(x)/q(x): Ep[f] = Eq[f·p/q]. It stays unbiased, but if q rarely produces outcomes that p considers likely, the weights explode and the variance with them. Outcome-sampling MCCFR (Section 1.7.7) is exactly this, and exactly this variance problem is its weakness.

                  1.3.2 Duplicate deals and common random numbers

                  Most of the variance in poker results is the cards, not the decisions. Duplicate play removes much of it: every deal is played twice with the seats swapped, so each player gets the good cards once and the bad cards once. If X1 is our result from the first playing and X2 from the swapped playing, the card luck in X1 and X2 is strongly negatively correlated, and

                  Var(X1 + X2) = Var X1 + Var X2 + 2 Cov(X1, X2), with Cov < 0.

                  The tournament scores duplicate matches, and the lab's harness plays duplicate pairs too, so lab numbers estimate exactly what the tournament measures. The reduction is never complete: once the two playings diverge (one player folds where the other called), the cards that follow differ in meaning.

                  The same idea compares two bots. To test whether A is better than B against opponent O, play A vs O and B vs O on the same seeds. Results share card luck, so the difference has much lower variance than two independent samples. This is called common random numbers.

                  A control variate is the third classic trick: subtract a quantity with known mean that is correlated with the noise. In poker, "chips won minus the all-in equity luck" (the expected value at the moment all chips went in, instead of the actual runout) is a standard example. Simple and powerful, but you must be sure the known mean is really zero.

                  Exercises 1.3

                  1. How many Monte Carlo samples give a ±0.5 percentage-point (1 SE) estimate of a 50% equity?
                  2. Var X1 = Var X2 = 2500 and the correlation is −0.6. What is the standard deviation of X1 + X2, compared with independent playings?
                  3. Why does comparing two bots on the same seeds reduce the variance of the difference?

                  1.4 Learning from a stream of evidence

                  A bot learns about its opponent during a match, one action at a time. Three tools make this precise: shrinkage (what to believe after few observations), sequential tests (when to act on the evidence), and classifiers (which of several opponent types we face).

                  1.4.1 Frequencies with a prior: Beta-Binomial shrinkage

                  Suppose the opponent faced a river bet n = 4 times and folded k = 3. Is their fold rate 75%? With so few samples, surely not exactly. Put a Beta prior on the fold rate p: a Beta(a, b) distribution behaves like "a folds and b calls seen before the match". The posterior after k folds in n tries is Beta(a+k, b+n−k), with mean

                  E[p | data] = (k + K·m) / (n + K), where m = a/(a+b) is the prior mean and K = a+b its strength.

                  With m = 0.4 and K = 15: (3 + 6)/(4 + 15) = 0.47, not 0.75. As n grows the data dominate. This shrinkage toward the prior is the principled version of "do not over-react to small samples". Pick K as the number of observations at which you would trust the data and the prior equally.

                  1.4.2 Deciding as soon as possible: the sequential probability ratio test

                  A fixed-sample test waits for n observations. Wald's sequential probability ratio test (SPRT) instead watches the running log-likelihood ratio Λt = Σs≤t log[P(ds|H1)/P(ds|H0)] and stops as soon as it crosses a boundary:

                  accept H1 when Λt ≥ log((1−β)/α);   accept H0 when Λt ≤ log(β/(1−α));   otherwise keep watching.

                  Here α is the tolerated false-positive rate and β the false-negative rate. With α = β = 0.05 both boundaries are at ± log 19 ≈ ± 2.94. Wald proved that the SPRT is optimal: no test with the same error rates needs fewer observations on average. The expected number of observations under H1 is about

                  E[N | H1] ≈ [(1−β) log((1−β)/α) + β log(β/(1−α))] / KL(H1 ‖ H0)

                  where the Kullback–Leibler divergence KL(p‖q) = Σx p(x) log(p(x)/q(x)) is the expected evidence per observation. Big divergence, fast decision.

                  Worked example. Opponent type H1 folds to a river bet 60% of the time; type H0 folds 30%. Per observation, KL = 0.6 ln(0.6/0.3) + 0.4 ln(0.4/0.7) = 0.416 − 0.224 = 0.192 nats. With α = β = 0.05: E[N] ≈ (0.95·2.944 − 0.05·2.944)/0.192 ≈ 14 river bets. But a river bet against this opponent might happen once every ten hands, so the decision takes about 140 hands, a third of a Stage-1 match. The lesson for an exploit layer: speed of identification is limited by how often the informative situation occurs. Combining evidence from every decision, not only one statistic, is how to be fast.

                  1.4.3 Many hypotheses at once: naive Bayes classification

                  With K candidate opponent types instead of two, keep one log-score per type: Sk = log P(type k) + Σt log P(dt | type k). The posterior is the softmax of the scores, P(type k | data) = eSk / Σj eSj. Treating the observations as independent given the type is the naive Bayes assumption. It is false (a player's actions within one hand are correlated) and makes the posterior over-confident, but the ranking of types is usually right and the method is fast and robust. The probabilities P(d | type k) are estimated from recorded games, with add-one (Laplace) smoothing so that an action never seen in training does not get probability zero (which would make a single surprise rule the type out forever).

                  Key idea

                  Evidence adds in log space. Shrink small-sample frequencies toward a prior. Decide sequentially with the SPRT; with many candidate types, keep a log-score per type. Detection speed is roughly (evidence per observation) × (observations per hand).

                  1.5 Poker mathematics

                  1.5.1 Heads-up no-limit Texas Hold'em, precisely

                  Two players. Each starts every hand with a stack of 200 chips (stacks reset each hand in our competition). One player is the button: they post the small blind (1 chip); the other posts the big blind (2 chips). Seats alternate every hand. The blinds are forced bets that create something to fight for.

                  Each player gets private hole cards. Then four betting rounds (streets) alternate with shared board cards: preflop (no board), the flop (3 cards), the turn (1 more), the river (1 more). Preflop the button acts first; on later streets the big blind acts first, so the button acts last, which is an advantage (position: you see what the opponent did before you decide).

                  On their turn a player may fold (give up the pot), check (pass, only if nothing is owed), call (match the opponent's bet), or raise (bet more; a first bet on a street is also a "raise" in our protocol). Amounts are "raise to": the total committed on this street. The minimum raise-to is the opponent's bet plus the size of the last bet or raise on this street (at least 2); the maximum is all-in. At most four bets or raises per street, and preflop the big blind counts as the first. A street ends when both have acted and the bets are equal. If nobody folded by the end of the river there is a showdown: each player makes the best five-card hand from their hole cards and the board; the better hand wins the pot (all chips bet), and equal hands split it.

                  Hand ranks, best first: straight flush, four of a kind, full house, flush, straight, three of a kind, two pair, one pair, high card. Ranks of individual cards: 2 lowest … A highest (an ace also plays low in the straight A-2-3-4-5).

                  1.5.2 Discard Hold'em

                  The competition variant changes one thing, but it changes a lot. Each player gets three hole cards. After the flop betting, if nobody folded, both players discard exactly one hole card simultaneously. Both discards are shown face up and removed from play. Then turn, river and showdown proceed as in Hold'em with two hole cards each. (If a discard is missing or illegal, the lowest-ranked card is discarded for you.)

                  Consequences worth noticing before any theory:

                  • You see the flop before you decide which two cards to keep, so starting hands are much more flexible than in Hold'em. Hand values are closer together preflop, and equities run closer.
                  • The discards are public information. The opponent's discarded card tells you something about the two they kept (they rarely throw away an ace that pairs the board). A thinking bot can read it; a careless bot leaks information through it.
                  • There is a non-betting decision (which card to throw) that costs time and can be solved separately by simulation.

                  1.5.3 Counting hands

                  The number of ways to choose k cards from n is the binomial coefficient C(n, k) = n!/(k!(n−k)!). Two hole cards from 52: C(52,2) = 1,326 combinations ("combos"). Three hole cards: C(52,3) = 22,100.

                  Many combos are strategically identical: before the flop, A♠K♠ and A♥K♥ differ only in suit names. Grouping by suit isomorphism (relabelling suits) gives 169 classes of two-card starting hands and 1,755 classes of three-card hands. This is a lossless reduction: nothing about the game is lost. Lossy reductions come later (Section 1.8).

                  On a Discard Hold'em river, from our point of view, the opponent's two kept cards are any two of the cards we have not seen: 52 − 5 (board) − 2 (our kept cards) − 1 (our discard) − 1 (their discard) = 43 cards, so C(43,2) = 903 possible holdings. Remember this number: a river is a small game.

                  1.5.4 Equity, pot odds and expected value

                  Your equity is your expected share of the pot if the hand went to showdown with no more betting: P(win) + ½ P(tie). Equity against a random hand is easy to estimate by Monte Carlo; equity against what the opponent actually holds is what matters, and that requires a model of them (Section 1.5.5).

                  Pot odds. The pot holds P chips, including the opponent's bet, and calling costs c. If you call and the hand goes to showdown with equity e:

                  EV(call) = e·(P + c) − c,   so calling is profitable iff e > c/(P+c).

                  The threshold c/(P+c) is the pot odds. Example: the pot was 100, the opponent bets 50 (so P = 150), calling costs 50: you need 50/200 = 25% equity. Facing a pot-sized bet (pot 100, bet 100): 100/300 = 33%.

                  Fold equity. A bet can win immediately if the opponent folds. Betting b into a pot P with zero equity (a pure bluff) breaks even when the opponent folds with probability

                  α = b / (P + b).

                  A half-pot bluff needs 33% folds; a pot-sized bluff 50%; a 2× pot overbet 67%. Real bets combine both: EV(bet) = f·P + (1−f)·[ecalled·(P+2b) − b], where f is the fold probability and ecalled our equity against the hands that call (usually lower than against all hands, because weak hands fold).

                  Value betting. A value bet is a bet that wants to be called because worse hands call. It is profitable when worse hands call more often than better hands do. A thin value bet is one that barely meets this.

                  1.5.5 Ranges and bluff-catching

                  Nobody knows the opponent's cards, so think in ranges: a probability distribution over all their possible holdings, given everything they did. Preflop, a player who raised has a stronger range than one who called. Each action re-weights the range by Bayes' rule: P(hand | action) ∝ P(action | hand)·P(hand). That is exactly the machinery of Section 1.2.1, with "hand" as the hypothesis.

                  The river is where this matters most, because nothing is left to come: your hand will not improve, and the decision is pure. Facing a river bet b into a pot P with a bluff-catcher (a hand that beats only bluffs), calling wins P+b against a bluff and loses b against value, so

                  call iff P(bluff | they bet) > b/(P + 2b).

                  Pot-sized bet: call if more than a third of their bets are bluffs. Many simple bots almost never bluff on the river; against them, folding bluff-catchers is free money. Many others bluff far too often; against them, calling is. A bot that cannot tell these apart loses chips at river showdowns. Hold that thought for Chapter 2.

                  The flip side is the minimum defence frequency (MDF): if you fold more than α = b/(P+b) of your range to a bet, the opponent profits by betting any two cards. To be unexploitable you must continue with at least 1 − α = P/(P+b) of your range. MDF is a defence against an unknown opponent; against a known non-bluffer it is a way to lose money. That is the first hint of the tension between equilibrium play and exploitation (Section 1.9).

                  One more ratio: the stack-to-pot ratio (SPR) = remaining stack / pot. Low SPR (≤ 2) means one more bet is all-in, so decisions become "commit or fold". High SPR leaves room for maneuvering.

                  1.6 Game theory beyond Nash

                  You know normal-form games and Nash equilibrium. This section builds what poker needs on top: games as trees with hidden information, best responses, exploitability, a complete small example, and the linear-programming view.

                  1.6.1 Two-player zero-sum games and the minimax theorem

                  Heads-up poker is a two-player zero-sum game: whatever one player wins the other loses. For such games von Neumann's minimax theorem says that with mixed strategies x, y and payoff matrix A (player 1's payoff),

                  maxx miny xTAy = miny maxx xTAy = v,

                  the value of the game. Three consequences make zero-sum games far nicer than general games:

                  1. Nash equilibria are exactly the pairs of maximin strategies: each player's equilibrium strategy guarantees at least their value against every opponent strategy, not just the equilibrium one.
                  2. Equilibria are interchangeable: if (x, y) and (x′, y′) are equilibria, so is (x, y′). There is no coordination problem; you do not need to guess "which" equilibrium the opponent plays.
                  3. Finding an equilibrium is a linear programme (Section 1.6.6), hence polynomial in the size of the game.

                  Poker is not symmetric hand by hand (the button has an advantage), but with seats alternating, and especially with duplicate deals, the two players' positions balance out and the value of the whole match is 0. So an equilibrium strategy cannot lose in expectation to anyone, over a duplicate pair. That is the entire appeal of equilibrium methods: a guarantee. Their weakness: the guarantee is "not lose", not "win a lot". Against a weak opponent an equilibrium wins only through the opponent's own mistakes, and usually far less than a strategy designed to exploit those mistakes.

                  1.6.2 Games as trees: extensive form and information sets

                  The extensive form describes a sequential game as a tree. Each node is a history h: the sequence of all actions so far, including the cards dealt. At each non-terminal history one player acts, or chance acts (deals cards) with known probabilities. Terminal histories z carry payoffs ui(z).

                  Poker has hidden information: you do not see the opponent's cards. An information set (infoset) I is the set of histories a player cannot tell apart when acting: same public actions, same own cards, any opponent cards. A strategy must choose the same action distribution at every history in an infoset, because the player does not know which one they are at. In our game, an infoset is roughly "my cards + the board + the betting sequence so far".

                  A behavioural strategy σi gives, for each infoset I of player i, a probability distribution σi(I, ·) over the actions available there. Poker satisfies perfect recall (nobody forgets what they saw or did), and for perfect-recall games Kuhn's theorem says behavioural strategies are as powerful as any mixed strategy. So "a strategy" from now on means a table: infoset → action probabilities.

                  The reach probability πσ(h) is the probability that history h occurs when everyone plays σ. It is a product of every probability along the path, and it factors by who chose each step: πσ(h) = π1σ(h)·π2σ(h)·πc(h), where πc is chance's contribution. We write π−i for the product of everyone's contribution except player i's (the opponent's and chance's). This factorisation is the engine of CFR.

                  1.6.3 Best response and exploitability

                  Fix the opponent's strategy σ2. A best response BR(σ2) is a strategy for player 1 that maximises their expected payoff against it. Computing it is easy when σ2 is known: walk the tree once; at each of our infosets, weight each history by the probability that the opponent and chance would have led there (π−1), and pick the action with the highest weighted value. A best response can always be pure (no randomisation needed).

                  The exploitability of a strategy profile σ = (σ1, σ2) in a zero-sum game measures how much a best-responding opponent would win:

                  expl(σ) = ½ [ maxσ′1 u1(σ′1, σ2) + maxσ′2 u2(σ1, σ′2) ]

                  (some authors omit the ½). It is zero exactly at a Nash equilibrium and positive otherwise. A profile with expl(σ) ≤ ε is an ε-Nash equilibrium. Exploitability is the honest scoreboard of any equilibrium solver. In poker it is reported in milli-big-blinds per hand (mbb/hand): with a 2-chip big blind, 1 mbb/hand = 0.002 chips/hand. Professional-level equilibrium approximations of full no-limit Hold'em sit around 1–10 mbb/hand; a careless bot can be exploitable for thousands.

                  The same machinery measures how far a bot is from optimal against a particular opponent: the gap between what it wins and what the best response to that opponent would win. Best response against a fixed, known opponent is the upper bound of exploitation.

                  1.6.4 A complete example: Kuhn poker

                  Kuhn poker is the smallest interesting poker game, and we will use it to check every algorithm by hand. Deck: three cards, J < Q < K. Each player antes 1 chip and gets one card; the third card is unused. Player 1 acts first: check or bet 1. If player 1 checks, player 2 may check (showdown for the antes) or bet 1, and then player 1 calls or folds. If player 1 bets, player 2 calls (showdown for 2 each) or folds. Higher card wins at showdown.

                  Kuhn poker has 12 infosets. Its equilibria are known in closed form. Player 1 picks a parameter α ∈ [0, ⅓]: bet a J with probability α (a bluff), always check a Q, bet a K with probability 3α; after check-bet, fold a J, call with a Q with probability α + ⅓, call with a K. Player 2's equilibrium is unique: facing a bet, call with K, call with Q with probability ⅓, fold J; facing a check, bet K, bet J with probability ⅓ (bluff), check Q. The value for player 1 is −1/18 ≈ −0.056 chips per hand: acting first is a disadvantage.

                  Notice what equilibrium play looks like: it bluffs with the worst hand at a precise frequency (⅓ for player 2) and calls with medium hands at a precise frequency. These frequencies make the opponent indifferent: player 2 bluffs J one-third of the time, which is exactly the frequency that makes player 1's Q indifferent between calling and folding. Indifference is the signature of mixed equilibria.

                  1.6.5 What equilibrium does not do

                  An equilibrium is a fortress, not an attack. Suppose player 2 in Kuhn poker never bluffs with J. The equilibrium player 1 keeps calling with Q a third of the time after check-bet, losing every time, because equilibrium play does not look at what the opponent does. The best response folds every Q there and wins more. In real poker against real bots the gap between "equilibrium" and "best response to this bot" is typically large: far larger than the equilibrium's own edge. This is the quantitative reason an exploit layer matters (Section 1.9).

                  1.6.6 The sequence form: poker as a linear programme

                  Converting an extensive-form game to a normal-form matrix is hopeless: the number of pure strategies is exponential in the number of infosets. The sequence form avoids this. A sequence of player i is the list of their own actions on the path to a node (for example "check, then call"). Instead of probabilities of whole strategies, the variables are realisation weights x(s): the probability that player i's own choices produce sequence s, assuming the other players and chance cooperate. They satisfy linear constraints: the empty sequence has weight 1, and at every infoset the weights of the extensions sum to the weight of the sequence leading there:

                  x(∅) = 1,   Σa ∈ A(I) x(sIa) = x(sI),   x ≥ 0,   i.e. Ex = e.

                  Expected payoff is bilinear: xTAy, where A[s, t] sums payoff × chance probability over terminal nodes reached by sequence pair (s, t). The matrix is sparse and has as many rows and columns as there are sequences, which is linear in the tree size. Equilibrium is then maxx miny xTAy subject to Ex = e, Fy = f, x, y ≥ 0. Dualising the inner minimisation (LP duality) turns this into one linear programme:

                  maximise fTq over (x, q) subject to FTq ≤ ATx,  Ex = e,  x ≥ 0.

                  The listing below solves Kuhn poker this way with SciPy and reproduces the value −1/18 (we ran it while writing this book; output: game value for player 1: -0.0556, and the solver happened to pick the α = 0 equilibrium: never bet J or K first, call a Q with probability ⅓ after check-bet).

                  """Kuhn poker solved exactly as a sequence-form linear programme (scipy.optimize.linprog).
Cards J=0, Q=1, K=2; each player antes 1; player 1 acts first; one bet of size 1.
Expected result: game value for player 1 = -1/18 = -0.0556."""
import itertools
import numpy as np
from scipy.optimize import linprog

CARDS = (0, 1, 2)
# Player 1 sequences: per card c, at the first decision: 'c:k' (check) or 'c:b' (bet);
# after check-bet: 'c:kc' (call) or 'c:kf' (fold).
seq1 = ["root"] + [f"{c}:{s}" for c in CARDS for s in ("k", "b", "kc", "kf")]
# Player 2 sequences: per card c, facing a check: 'c:k' or 'c:b'; facing a bet: 'c:c' or 'c:f'.
seq2 = ["root"] + [f"{c}:{s}" for c in CARDS for s in ("k", "b", "c", "f")]
i1 = {s: i for i, s in enumerate(seq1)}
i2 = {s: i for i, s in enumerate(seq2)}

# Constraints E x = e: root = 1; per card k + b = root; kc + kf = k.
E = np.zeros((1 + 2 * len(CARDS), len(seq1))); e = np.zeros(E.shape[0]); E[0, 0] = 1; e[0] = 1
for j, c in enumerate(CARDS):
    E[1 + 2 * j, i1[f"{c}:k"]] = E[1 + 2 * j, i1[f"{c}:b"]] = 1; E[1 + 2 * j, 0] = -1
    E[2 + 2 * j, i1[f"{c}:kc"]] = E[2 + 2 * j, i1[f"{c}:kf"]] = 1; E[2 + 2 * j, i1[f"{c}:k"]] = -1
F = np.zeros((1 + 2 * len(CARDS), len(seq2))); f = np.zeros(F.shape[0]); F[0, 0] = 1; f[0] = 1
for j, c in enumerate(CARDS):
    F[1 + 2 * j, i2[f"{c}:k"]] = F[1 + 2 * j, i2[f"{c}:b"]] = 1; F[1 + 2 * j, 0] = -1
    F[2 + 2 * j, i2[f"{c}:c"]] = F[2 + 2 * j, i2[f"{c}:f"]] = 1; F[2 + 2 * j, 0] = -1

# Payoff matrix A (player 1's payoff), summed over the 6 deals with chance probability 1/6.
A = np.zeros((len(seq1), len(seq2)))
for c1, c2 in itertools.permutations(CARDS, 2):
    w, sd = 1 / 6, (1 if c1 > c2 else -1)
    A[i1[f"{c1}:k"], i2[f"{c2}:k"]] += w * sd          # check, check: showdown for the antes
    A[i1[f"{c1}:kf"], i2[f"{c2}:b"]] += w * -1        # check, bet, fold
    A[i1[f"{c1}:kc"], i2[f"{c2}:b"]] += w * 2 * sd    # check, bet, call: showdown for 2
    A[i1[f"{c1}:b"], i2[f"{c2}:f"]] += w * 1          # bet, fold
    A[i1[f"{c1}:b"], i2[f"{c2}:c"]] += w * 2 * sd     # bet, call

# max_x min_y x^T A y  s.t. E x = e, F y = f, x, y >= 0.  Dualise the inner min over y:
# min_y (A^T x)^T y s.t. F y = f, y >= 0  ==  max_q f^T q s.t. F^T q <= A^T x.
# So: maximise f^T q over (x, q) with -A^T x + F^T q <= 0, E x = e, x >= 0, q free.
n1, nq = len(seq1), F.shape[0]
c = np.concatenate([np.zeros(n1), -f])
A_ub = np.hstack([-A.T, F.T]); b_ub = np.zeros(len(seq2))
A_eq = np.hstack([E, np.zeros((E.shape[0], nq))])
bounds = [(0, None)] * n1 + [(None, None)] * nq
res = linprog(c, A_ub=A_ub, b_ub=b_ub, A_eq=A_eq, b_eq=e, bounds=bounds, method="highs")
x = res.x[:n1]
print(f"game value for player 1: {-res.fun:.4f} (exact -1/18 = {-1/18:.4f})")
for c_ in CARDS:
    k, b = x[i1[f'{c_}:k']], x[i1[f'{c_}:b']]
    call = x[i1[f'{c_}:kc']] / k if k > 1e-9 else float('nan')
    print(f"P1 with {'JQK'[c_]}: bet {b:.3f}, after check-bet call {call:.3f}")

                  Key idea

                  In two-player zero-sum games, equilibrium strategies are maximin strategies: they guarantee the game's value against everyone, and in a seat-balanced match that value is 0. Exploitability (what a best response would win) is the measure of distance from equilibrium. The sequence form makes equilibrium an LP whose size is linear in the game tree.

                  1.7 Regret, CFR and MCCFR

                  This is the heart of modern poker AI. We build it in four steps: regret in a one-shot repeated choice; regret matching and its bound; why self-play with low regret gives an equilibrium; and how CFR decomposes the regret of a whole game tree into local regrets at each infoset.

                  1.7.1 Regret

                  Consider a repeated decision. At each round t = 1, …, T you choose a mixed strategy σt over a finite action set A; then the environment (possibly an adversary) reveals a utility ut(a) for every action. Your expected utility is ut(σt) = Σa σt(a) ut(a). The regret for not having always played action a is

                  RT(a) = Σt=1T [ ut(a) − ut(σt) ].

                  This is external regret: hindsight against the best fixed action. An algorithm is no-regret if maxa RT(a)/T → 0 for every sequence of utilities, even an adversarial one. That is a strong guarantee: in the long run you do as well as the best fixed action chosen with hindsight.

                  1.7.2 Regret matching and its bound

                  Regret matching (Hart and Mas-Colell, 2000) plays each action in proportion to its positive cumulative regret:

                  σT+1(a) = [RT(a)]+ / Σb [RT(b)]+,  or uniform if no regret is positive.

                  A tiny example. Rock-paper-scissors against an opponent who always plays Rock. Round 1: uniform; utilities R 0, P +1, S −1; we expect 0; regrets become (0, +1, −1). Round 2: only P has positive regret, so we play Paper with probability 1 and get +1; adding u(a) − 1 gives regrets (−1, +1, −3). We keep playing Paper. Regret matching found the best response in one step.

                  Theorem. If utilities lie in an interval of width Δ, regret matching guarantees maxa RT(a) ≤ Δ √(|A| T), so average regret falls like 1/√T.

                  Proof sketch. Write rt(a) = ut(a) − ut(σt) for the instantaneous regret vector, so Rt = Rt−1 + rt. Track the potential Φt = ‖[Rt]+‖2 = Σa ([Rt(a)]+)2.

                  1. For real numbers, ([x+y]+)2 ≤ ([x]+ + y)2 (if x+y ≤ 0 the left side is 0; otherwise 0 < x+y ≤ [x]++y). Summing over actions: Φt ≤ ‖[Rt−1]+ + rt‖2 = Φt−1 + 2 [Rt−1]+·rt + ‖rt‖2.
                  2. The cross term is zero. σt is proportional to [Rt−1]+, and Σa σt(a) rt(a) = ut(σt) − ut(σt) = 0. (If all regrets are non-positive the cross term is trivially 0.)
                  3. Each |rt(a)| ≤ Δ, so ‖rt‖2 ≤ |A|Δ2. By induction, ΦT ≤ T|A|Δ2.
                  4. Finally maxa RT(a) ≤ ‖[RT]+‖ = √ΦT ≤ Δ√(|A|T). ∎

                  The geometric picture (Blackwell approachability): regret matching always steps so that the regret vector does not move "outward" from the negative orthant faster than its own noise, and the noise only grows like √T.

                  1.7.3 From low regret to equilibrium

                  Let both players of a zero-sum game run a no-regret algorithm against each other (self-play). Let x̄ = (1/T)Σxt and ȳ = (1/T)Σyt be the average strategies, and suppose each player's average regret is at most ε.

                  Claim. (x̄, ȳ) is an ε-Nash equilibrium in the sense of Section 1.6.3 (exploitability ≤ ε with the ½ convention).

                  Proof sketch. Player 1's regret bound says, for every fixed x′: (1/T)Σt u(x′, yt) − (1/T)Σt u(xt, yt) ≤ ε. Because u is linear in y, the first average equals u(x′, ȳ). So maxx′ u(x′, ȳ) ≤ ū + ε, where ū is the average realised payoff. Symmetrically, player 2's bound gives miny′ u(x̄, y′) ≥ ū − ε. Subtract: maxx′ u(x′, ȳ) − miny′ u(x̄, y′) ≤ 2ε, which is twice the exploitability. ∎

                  Pitfall

                  It is the average strategy that converges, not the current one. In rock-paper-scissors self-play, the current strategies of two regret-matching players spiral around the equilibrium forever; only their averages settle at (⅓, ⅓, ⅓). Shipping the current strategy instead of the average is a classic bug. (CFR+ is an exception in practice: its current strategy is often good too.)

                  1.7.4 Counterfactual regret minimisation

                  Running regret matching on the whole game's pure strategies is hopeless: too many of them. Counterfactual regret minimisation (CFR; Zinkevich, Johanson, Bowling and Piccione, 2007) runs a separate regret matcher at every infoset, with a carefully chosen local utility.

                  Define the counterfactual value of player i at infoset I under profile σ:

                  vi(σ, I) = Σh ∈ I π−iσ(h) · Σz terminal below h πσ(h → z) · ui(z)

                  In words: the expected payoff from I onward, weighting each history in I by the probability that chance and the opponent would bring us there, as if we had played to reach I on purpose. That is the "counterfactual". Let vi(σ, I, a) be the same with action a forced at I. The instantaneous counterfactual regret is rt(I, a) = vi(σt, I, a) − vi(σt, I); cumulate it, and set σt+1(I, ·) by regret matching on the cumulative values.

                  Theorem (Zinkevich et al.). Player i's overall regret is at most the sum over their infosets of the positive parts of these local counterfactual regrets. Hence average overall regret ≤ Δ |𝓘i| √|A| / √T, where |𝓘i| is the number of infosets, and by Section 1.7.3 the average strategy profile converges to a Nash equilibrium.

                  Why the decomposition works (idea). Compare our actual strategy with the best deviation σ′. Change our strategy one infoset at a time, from the bottom of the tree upward. Changing the choice at infoset I changes our payoff only in the subtree below I, and the weight of that subtree is πi(I)·π−i. Our own reach πi(I) ≤ 1, so the gain from deviating at I is at most the counterfactual (opponent-and-chance-weighted) gain, which is exactly the counterfactual regret. The total gain of the full deviation telescopes into the sum of these local gains. Weighting by π−i but not πi is what makes each infoset's problem independent of how likely we are to reach it.

                  The average strategy at each infoset must be weighted by our own reach probability: σ̄(I, a) = Σt πiσt(I) σt(I, a) / Σt πiσt(I). This is the behavioural form of averaging the realisation plans of Section 1.6.6.

                  The algorithm is one recursive tree walk per iteration:

                  def cfr(h, i, pi_i, pi_opp):           # returns player i's value at history h
    if terminal(h): return u_i(h)
    if chance(h):   return sum(p * cfr(h+c, i, pi_i, pi_opp * p) for c, p in outcomes(h))
    I = infoset(h); sigma = regret_matching(R[I])
    if player(h) == i:
        v_a = {a: cfr(h+a, i, pi_i * sigma[a], pi_opp) for a in actions(I)}
        v = sum(sigma[a] * v_a[a] for a in actions(I))
        for a in actions(I):
            R[I][a]  += pi_opp * (v_a[a] - v)           # counterfactual regret
            S[I][a]  += pi_i * sigma[a]                 # average-strategy numerator
        return v
    else:
        return sum(sigma[a] * cfr(h+a, i, pi_i, pi_opp * sigma[a]) for a in actions(I))
# one iteration: cfr(root, 0, 1, 1); cfr(root, 1, 1, 1)
# answer: S normalised at every infoset

                  Each iteration visits every node of the tree once per player. Memory: two tables (cumulative regret R, cumulative strategy S) of size (number of infosets × actions).

                  1.7.5 CFR+ and friends

                  Three small changes make CFR dramatically faster in practice. Together they are CFR+ (Tammelin, 2014):

                  • Regret flooring: after each update, clip cumulative regrets at zero (Q ← max(Q + r, 0)). An action that was bad for a long time can then recover immediately when it becomes good, instead of first working off a huge negative debt.
                  • Linear averaging: weight iteration t by t in the average strategy, so the bad early iterations fade.
                  • Alternating updates: update player 1, then player 2 against player 1's new strategy.

                  CFR+ is what Cepheus (2015) used to essentially solve heads-up limit Hold'em. Its empirical convergence is often closer to 1/T than 1/√T. Discounted CFR (DCFR; Brown and Sandholm, 2019) generalises the weighting (positive regrets × t1.5/(t1.5+1), negative regrets × ½, averages × t2) and is a good default today.

                  1.7.6 The vector form: ranges as arrays

                  Poker has special structure: the betting tree is public, and the only hidden information is each player's private cards. So instead of walking one history at a time, walk the public tree (betting actions and board cards) and carry at each public node a vector indexed by every possible private hand:

                  • a range vector ri[h]: player i's reach probability for each of their hands h (their range, unnormalised);
                  • a counterfactual value vector vi[h];
                  • a strategy matrix σ[h, a] and a regret matrix R[h, a] at each node where i acts.

                  At a terminal node the counterfactual values come from the opponent's range vector. If the opponent folded and the pot gives us w: v[h] = w · Σh′ compatible with h ropp[h′]. At a showdown: v = w·(M ropp), where M[h, h′] is +1 if h beats h′, −1 if it loses, 0 for a tie or when the hands share a card. Everything else is elementwise: multiply ranges by strategy columns going down, sum value vectors weighted by the strategy coming up, update regrets with whole-row operations.

                  A river subgame of Discard Hold'em has 903 possible holdings per player (Section 1.5.3), so M is 903 × 903 ≈ 815,000 entries and a showdown is one matrix-vector product. A betting tree with two or three bet sizes has a few dozen public nodes. One CFR iteration is then a few dozen small array operations and a handful of matrix-vector products. That is ideal for NumPy, and for a GPU when batched over many subgames. This is how real-time poker solvers work, and Chapter 2 measures it.

                  The sort trick: when all hands are ranked by strength, the showdown value of hand h is (opponent mass below h) − (opponent mass above h), computable with a cumulative sum in O(n) instead of O(n2), plus a correction for card-overlap (blockers).

                  1.7.7 Monte Carlo CFR

                  Full-width CFR touches every node every iteration. For big games that is too slow per iteration. Monte Carlo CFR (MCCFR; Lanctot et al., 2009) samples part of the tree per iteration and uses importance weights (Section 1.3.1) so that the sampled counterfactual values are unbiased estimates of the true ones. Regret matching on unbiased noisy regrets still converges, at the same 1/√T rate in expectation but with a larger constant from the noise.

                  • Chance sampling: sample the cards once per iteration, walk all betting actions. Natural for poker; cost per iteration = size of the betting tree.
                  • External sampling: sample chance and the opponent's actions (from their current strategy); explore all of the updating player's actions. The opponent's and chance's reach weights then cancel against the sampling probabilities, so no explicit importance weights are needed. This is the usual default: low variance, cost per iteration roughly the square root of the tree.
                  • Outcome sampling: sample a single path from root to leaf, with some exploration ε for the updating player, and divide by the path's sampling probability. Cheapest per iteration and usable online, but the 1/q weights make the variance large.

                  The trade-off is always iterations per second × progress per iteration. In a big game MCCFR wins on wall-clock time; in a small game, vectorised full-width CFR+ wins easily.

                  1.7.8 Measuring a solver

                  In small games (Kuhn, Leduc, a single river subgame) compute exact exploitability with a best-response traversal; it must fall towards 0. In large games exact best response is impossible, so use lower bounds such as local best response (LBR: a greedy exploiter that looks one action ahead) and head-to-head matches against reference bots. A solver that is not checked on a small game with known value is not to be trusted on a large one. The repository's Leduc test (Chapter 2) is exactly this check.

                  Key idea

                  Regret matching at every infoset, driven by counterfactual values (weighted by opponent and chance reach only), makes the average strategy converge to equilibrium at rate 1/√T, with a constant proportional to the number of infosets. CFR+ is faster in practice. In poker, carry range vectors over the public tree so that every step is an array operation. MCCFR samples to make huge trees affordable, at the price of variance.

                  1.8 Abstraction, subgame solving and PIMC

                  Full no-limit Hold'em has about 10160 histories; Discard Hold'em is larger. No algorithm touches that. Every practical poker AI therefore solves a smaller game that approximates the real one, and then uses the solution with care.

                  1.8.1 Card abstraction

                  A card abstraction groups private-card situations into buckets that share one strategy. Common bucketing features:

                  • Equity (often called expected hand strength, E[HS]): the hand's equity against a uniformly random opponent hand with the remaining board dealt at random. Cheap, but it confuses a made medium hand with a draw of the same equity.
                  • Equity distribution: a histogram of the hand's equity over the possible next cards. Clustering these histograms with k-means under the earth mover's distance (EMD) gives potential-aware buckets that separate draws from made hands.

                  Abstractions are usually imperfect-recall: the bucket on the turn does not remember the bucket on the flop. This saves enormous memory but voids CFR's convergence guarantee (in practice it still works well).

                  1.8.2 Action abstraction and translation

                  No-limit betting allows any amount, so an action abstraction keeps only a few sizes, such as half pot, pot and all-in. When the opponent bets a size that is not in the abstraction (an off-tree action), the bot must map it to nearby sizes in its tree: action translation. The standard pseudo-harmonic mapping treats a bet of x (as a fraction of the pot) between abstract sizes A < x < B as size A with probability

                  f(x) = ((B − x)(1 + A)) / ((B − A)(1 + x))

                  and as B otherwise. It is designed so that bets cannot be cheaply exploited by choosing sizes in the gaps.

                  Pitfall: abstraction error

                  A strategy's exploitability in the real game = its error in solving the abstract game + the abstraction's own error. More CFR iterations shrink only the first term. A badly chosen abstraction can make a perfectly solved abstract strategy lose to simple real-game bots. Even refining an abstraction can increase real-game exploitability (an abstraction pathology). This is exactly the failure Chapter 2 documents for the repository's CFR attempt.

                  1.8.3 Subgame solving

                  Modern superhuman bots (Libratus 2017, Pluribus 2019, DeepStack 2017) do not play a fixed precomputed strategy. They use a coarse blueprint strategy for early decisions and then re-solve the remaining game in real time, with a finer abstraction, when they get there.

                  A subgame is the game from some public node onward (for example "the river, after this betting and this board"). To solve it you need the players' ranges on entry, which come from the blueprint's reach probabilities (Section 1.6.2). Two flavours:

                  • Unsafe subgame solving assumes the opponent's range on entry is exactly what the blueprint predicts and solves the subgame as a fresh game. It is simple and often works, but an opponent who reaches the subgame with a different range can exploit it.
                  • Safe subgame solving adds a "gadget": at the root of the subgame the opponent may take a fixed payoff equal to what their hand was worth under the blueprint. The re-solved strategy is then never worse than the blueprint against any opponent. Variants (re-solving, max-margin, reach subgame solving) trade safety against how much they can improve.

                  The river is the natural subgame: no cards remain, the hand counts are small (903 per player in Discard Hold'em), and the vector form of CFR (Section 1.7.6) solves it in milliseconds. The entry ranges do not have to come from a CFR blueprint: any model of both players' ranges works, for example ranges inferred from the opponent's actions. The solution is then an equilibrium of that river given those ranges, which is a strong, principled way to make the hardest decision in the game.

                  1.8.4 Perfect-information Monte Carlo

                  Perfect-information Monte Carlo (PIMC) is the simplest way to act under hidden information: sample many "worlds" (complete guesses of the hidden cards) from your belief, find the best action in each world as if everything were visible, and pick the action that is best on average. It is used for card games like bridge and Skat, and it works well for decisions where hiding information does not matter, such as which card to discard (both discards are revealed anyway). It has two known flaws. Strategy fusion: in each sampled world it assumes it can choose differently per world later on, which it cannot. Non-locality: it ignores that the opponent's past actions were chosen knowing their cards. For betting decisions both flaws matter; for a discard they matter much less.

                  1.9 Exploitation theory

                  Equilibrium is a guarantee; exploitation is how you win a lot. This section is the theory of exploiting safely: how to model an opponent, how hard to lean on the model, how to notice when the model is wrong, and what to optimise when the scoring rule is "win the match", not "win chips".

                  1.9.1 Opponent models

                  An opponent model is a prediction of what the opponent does in each situation. Three levels of ambition:

                  1. Frequency statistics per spot: fold-to-river-bet, raise-when-checked-to, and so on, each shrunk toward a prior (Section 1.4.1). Cheap and robust, but blind to which hands take each action.
                  2. Action given hand: P(action | hand strength, spot), learned from hands that reached showdown. This is what is needed to infer ranges and to know what a bet "means". Data are scarce: you only see cards at showdown, and the hands you see are a biased sample (a bluff that you folded to is never shown).
                  3. A library of types: a fixed set of known opponent styles, each with a full predicted strategy, and an online classifier over them (Section 1.4.3). Once the type is identified, the counter-strategy is precomputed. This trades flexibility for speed: identification can happen in tens of hands instead of hundreds.

                  1.9.2 Best response to a model, and its danger

                  Given a model σ̂2, the best response BR(σ̂2) maximises expected winnings if the model is right. If it is wrong it can be catastrophic: a best response is typically a pure, extreme strategy (always fold here, always bluff there), and extreme strategies are highly exploitable. An opponent who adapts, or simply differs from the model, punishes it.

                  Restricted Nash response (RNR; Johanson, Zinkevich and Bowling, 2007) is the principled middle ground. Build a modified game in which, with probability p, the opponent is forced to play the model σ̂2, and with probability 1 − p they play freely. Solve that game for an equilibrium. The resulting strategy for us:

                  • at p = 0 is an ordinary equilibrium (unexploitable, exploits nothing);
                  • at p = 1 is the best response to the model (maximally exploiting, maximally exploitable);
                  • in between traces a curve of strategies that, for each level of worst-case loss, exploit the model as much as possible. Empirically the curve is very favourable: you get most of the exploitation for a small increase in exploitability.

                  Data-biased response (DBR) refines this by making p depend on how much data supports the model at each infoset: trust frequent spots, ignore rare ones.

                  Safe exploitation (Ganzfried and Sandholm, 2015) takes another angle: only risk what you have already won. Track how far above the game value you are (the "gifts" the opponent has given you by their mistakes); you may deviate from equilibrium to exploit, as long as the worst case of the deviation is covered by gifts already banked. The strategy then provably never does worse than the game value in expectation, yet exploits.

                  1.9.3 Noticing that the model is wrong

                  Opponents change style (some bots switch modes when losing), and classifiers make mistakes. A bail-out monitor watches for evidence against the current model. The standard tool is Page's CUSUM (cumulative sum) test: with ℓt = log[P(dt | "changed") / P(dt | model)], keep St = max(0, St−1 + ℓt) and raise an alarm when St exceeds a threshold. It is the SPRT restarted at zero whenever the evidence favours the model, which makes it quick to detect a change at any point in the match. Results can also be monitored directly: if a counter-strategy that should win +5 chips/hand is at −2 after 100 hands, the CLT of Section 1.2.2 says how surprising that is.

                  1.9.4 How hard to exploit: grade by confidence

                  Put the pieces together and you get a policy: the strength of exploitation λ ∈ [0, 1] grows with the posterior confidence in the opponent model (or type), and drops back on a bail-out alarm. λ can parameterise an RNR-like mixture (p = λ), a mix between the base strategy and the counter-strategy, or the size of parameter shifts (call thresholds, bluff frequencies). "Caught" should mean "confident", never "assumed".

                  1.9.5 Optimise the probability of winning the match

                  The tournament awards a point for winning a match, not for chips. Over n hands with per-hand edge μ and per-hand standard deviation σ (after duplicate variance reduction), the CLT gives

                  P(win match) ≈ Φ(μ √n / σ),

                  where Φ is the standard normal distribution function. Example: μ = 1 chip/hand, σ = 50, n = 400: Φ(0.4) ≈ 0.66. Doubling the edge to 2 gives Φ(0.8) ≈ 0.79; doubling the match length instead gives Φ(0.57) ≈ 0.71. Three consequences shape an exploit layer:

                  1. Edge matters only through μ/σ. A risky exploit that raises μ but raises σ even more can lower P(win).
                  2. State-dependence. When ahead late in a match, reduce variance; when behind, increase it. The extreme form is the endgame lock: once the lead exceeds the most you can lose by check-folding every remaining hand (the blinds), check-folding guarantees the win.
                  3. Capped tie-break. If ties on points are broken by chips clipped at ±C per match, winning a match by more than C earns nothing. Margin beyond the cap is wasted risk.
                  Key idea

                  Exploit in proportion to confidence; prefer RNR-style strategies that keep most of the gain at little worst-case cost; watch for model failure with CUSUM; and aim at P(win), which rewards edge per unit of variance, not raw edge.

                  1.10 Self-improvement: self-play, leagues and honest evaluation

                  The Rocket League recipe ("make the bot face a slightly better bot, and keep learning") is a form of self-play. It works when skill is roughly transitive. Poker exploitation is not, so the recipe needs care. This section gives the tools.

                  1.10.1 Self-play and fictitious play

                  In fictitious play (Brown, 1951) each player best-responds to the empirical average of everything the opponent has played so far. In two-player zero-sum games the averages converge to equilibrium (Robinson, 1951), slowly. CFR self-play (Section 1.7.3) is a faster cousin. Naive self-play, "train against your latest self", has no such guarantee: it can chase its own tail.

                  1.10.2 Non-transitivity

                  A relation is transitive if A beats B and B beats C imply A beats C. Rock-paper-scissors is the standard counterexample, and poker strategies are full of such cycles. A calling station beats a heavy bluffer (it calls every bluff down). A heavy bluffer beats a tight player (who folds too often to its bets). A tight value-better beats a calling station (it bets its good hands and gets paid every time). Training only against your latest version can walk round a cycle: each new version beats the previous one and is no better overall. Large-scale studies of games describe a spinning top geometry: a transitive "skill" axis plus cyclic structure that is widest at intermediate skill. Real progress means climbing the skill axis, not running round the cycles.

                  1.10.3 Populations: double oracle, PSRO and leagues

                  The fix is to train against a population, not one opponent.

                  • Double oracle and its generalisation PSRO (policy-space response oracles; Lanctot et al., 2017) keep a population of strategies and a matrix of their head-to-head results (the meta-game). They solve the meta-game for a Nash mixture, train a new best response against that mixture, add it to the population, and repeat. With exact best responses this converges to a Nash equilibrium of the full game.
                  • A league (AlphaStar, 2019) runs several roles at once. Main agents train against a mixture of all past agents, weighted towards those they struggle against (prioritised fictitious self-play). Main exploiters train only to beat the current main agents, exposing their weaknesses. League exploiters train to beat the whole league. Past agents stay frozen in the pool, so nothing is forgotten.

                  The Rocket League bots you have seen are trained with deep reinforcement learning (typically the PPO algorithm) on billions of frames against earlier versions of themselves. That works because the compute is enormous and the skill is mostly transitive (better car control beats worse). With little compute, the parameter-space version of a league is the realistic analogue: the "agents" are parameter settings of a fixed decision procedure, and "training" is search.

                  1.10.4 Ratings

                  The Elo rating (or the equivalent Bradley–Terry model) assumes P(A beats B) = 1/(1 + 10−(RA−RB)/400): one number per player, so it assumes transitivity. With cycles, Elo averages them away and can rank a bot highly because it farms one weak opponent. Report the full matrix of head-to-head results, or a meta-game Nash mixture (Nash averaging), instead of a single rating.

                  1.10.5 Search under noise, and overfitting

                  Parameter search with noisy evaluations is a well-studied problem. Useful tools:

                  • Random search and evolution strategies such as CMA-ES (which adapts a Gaussian search distribution towards good regions) need only "evaluate this setting".
                  • Successive halving and Hyperband: evaluate many candidates cheaply, keep the best half, evaluate those more, and repeat. The sample budget concentrates on promising candidates. This is the main defence against the cost arithmetic of Section 1.2.3.
                  • Bandit algorithms (UCB: pick the candidate with the best optimistic bound) do the same allocation adaptively.

                  Every search overfits. If you pick the best of 50 variants by its measured edge against a training pool, the edge is overstated (winner's curse) and specific to that pool. Three guards:

                  1. re-test the winner on fresh seeds before believing it;
                  2. keep a held-out set of opponents that the search never sees, and look at it rarely. Once you design anything from what you saw in the held-out results, it is no longer held out;
                  3. use an acceptance gate that also requires "no opponent got worse by more than 2 SE", so a variant cannot buy a gain against one bot with a loss against another.
                  Key idea

                  Self-improvement must be population-based (past champions, exploiters and external opponents) because poker is non-transitive. Budget evaluations with successive halving, gate every promotion on fresh seeds and no regressions, and protect a held-out set.

                  2.2 One match, end to end

                  The tournament engine starts python3.11 bot.py. bot.py calls bot/main.py, which loads the default brain (DEFAULT_BRAIN = "tier3", bot/main.py:42), replaces sys.stdout with stderr so that a stray print cannot corrupt the protocol (Section 1.1.1), and enters a loop: read one line, handle it, maybe write one line.

                  The wire protocol (docs/rules/protocol.pdf) is JSON lines. The engine sends init (match length, time bank, blinds), then per hand new_hand (seat, three hole cards), action_request, discard_request, discard_result and hand_result, and finally match_end. The bot answers only requests: {"type":"action","action":"raise","amount":40} or {"type":"discard","card":"Kd"}.

                  The adapter (bot/protocols/pokerbots.py) translates. Its one subtle job: the real protocol never sends the opponent's action as a separate message. The opponent's moves appear only inside the history list of the next request. So the adapter remembers how much of the history it has already turned into messages and emits the new entries. At a discard request the opponent's last action (the one that closed the flop betting) is not in any history yet. The adapter infers it (they must have called our bet, or checked behind our check) and emits it before the discard request (pokerbots.py:223). Inference of a missing fact from the rules is a recurring theme; when it fails, the bot's view of the hand would be wrong, so the inference is covered by tests.

                  GameState (bot/state.py) accumulates messages into a record of the hand: our cards, the board, the pot, every action (street, actor, action), the opponent's revealed discard and their cards at showdown. Brains see only this neutral record, never the wire format. One consequence: the same brain plays every wire format and every variant spec.

                  2.3 Never forfeit: the safety layers and the time bank

                  A crash, an over-long reply, or an exhausted time bank forfeits the match (Section 1.1.6). The bot has three layers of defence (bot/main.py):

                  1. The brain runs in try/except. Any exception falls back to Tier 0: check if free, else fold; for a discard, the rules' own fallback (the lowest card). Tier 3 adds an inner layer: if its own logic fails, Tier 2 decides (bot/brains/tier3.py:221).
                  2. Every action is validated and clamped to the legal set before it is sent: an over-sized raise becomes the maximum, an illegal call becomes a check, a non-action becomes Tier 0.
                  3. A hard deadline interrupts the brain with a signal alarm, and an emergency mode skips the brain entirely when the bank is nearly empty.

                  The main loop never lets an exception escape. A line it cannot parse is answered anyway: a blind check to a broken action request, the lowest card to a broken discard request (pokerbots.py:301), because silence forfeits.

                  Pacing (bot/timing.py) is a small control law. Per decision:

                  budget = min( usable bank / (hands left × 5.5 decisions) / 5.5 safety,  0.25 s,  1.2 × opening pace )

                  where "usable" keeps 10% of the bank in reserve and "opening pace" is the same formula at the start of the match. The cap at 1.2× the opening pace stops the bot from spending early savings late (left uncapped, the last hands ran 10× the budget of the first). The hard limit is a multiple of the budget, never more than 1.5 s, nor more than 0.3× the 5-second reply limit. The engine's own time_left_ms on every request is authoritative, so the controller tracks the real clock. Reported results: 23–33% of the bank used, projected for a server twice as slow; worst reply about 40 ms; about 40 MB of memory against a 1 GB limit. Measured for this book on a 1,000-hand bench: 49% of a 60-second bank projected at 2× slower, which is close to the 50% guard line. It fits the real Stage 2 bank (150 s for about 1,000 hands) comfortably.

                  2.4 Perception: what the bot knows at a decision

                  Before any strategy, the bot builds a Situation (bot/situation.py): everything about this decision that is not strategy. Its parts map directly onto Chapter 1.

                  2.4.1 Reconstruction

                  The bot re-plays the hand inside its own copy of the game rules (bot/sim/replay.py), with placeholder tokens for the cards it has not seen. This "reconstruction" lets every later step simulate the rest of the hand exactly as the engine would: the same rules code runs in the lab engine and inside the bot (bot/game/).

                  2.4.2 Equity

                  At the first decision of a hand, equity comes from a precomputed table: for each of the 1,755 suit-isomorphism classes of three-card hands (Section 1.5.3), the expected showdown share against a random hand, estimated offline by Monte Carlo with 6,000 samples per class (Section 1.3.1), plus the same against the top 30% of hands. The table is embedded into bot/embedded.py (the bot may not read files) and comes from data/discard_holdem/, which is committed since 31 October. Later decisions estimate equity by sampling the hidden cards and playing the hand out to the end (bot/sim/share.py, bot/sim/rollout.py), within the time budget.

                  2.4.3 Inference: the opponent's range

                  Sampling hidden cards uniformly would ignore everything the opponent did. bot/sim/inference.py weights each sampled opponent hand by how likely the opponent's visible choices were with it: exactly the range update P(hand | actions) ∝ P(actions | hand)·P(hand) of Section 1.5.5, done with importance weights (Section 1.3.1). The model of P(action | hand) is a "self-model": the opponent is assumed to play sensibly. Bets and raises are more likely with strong hands (a softmax over hand strength with sharpness γ), and a discard is more likely if it keeps good cards (sharpness β). If the weights collapse (low effective sample size), it falls back to unweighted sampling.

                  Because a maniac does not play sensibly, the model carries a trust level. After every showdown, the revealed hand is scored: how much more likely were the opponent's choices under the model than under random play? Trust scales γ and β, so inference fades out against opponents it does not describe. This is a small, real instance of the "notice that the model is wrong" principle of Section 1.9.3.

                  2.4.4 Opponent statistics

                  bot/opponent.py and bot/strategy/oppstats.py keep frequency statistics per spot (fold to a flop bet, fold to a river bet by bet size, raise against a limp, c-bet, check-raise, and so on). Each is shrunk toward a population prior "worth 15 observations" (Section 1.4.1; the priors describe a typical LLM-written bot). A spot may move play only after 20 real observations, and by at most 15 percentage points: a deliberate brake against the small-sample noise of Section 1.2.2.

                  One statistic deserves its name: the bluff index. Of the opponent's turn and river bets that reached showdown, it is the share whose hand was weak (below the 50th percentile of all two-card hands on that board). It is the empirical input to the bluff-catching rule of Section 1.5.5. It has a built-in bias: bluffs that we folded to are never shown, so the index underestimates bluffing. Shrinkage and the prior partly compensate.

                  2.5 The brains: Tier 0 to Tier 3

                  A brain is a policy: Situation and legal actions in, one action out. The tiers build on each other by inheritance.

                  2.5.1 Tier 1: equity against pot odds

                  Tier 1 is Section 1.5.4 turned into code. The whole betting rule (bot/brains/tier1.py:115):

                  if legal.can_raise and eq >= per_street(p["raise_equity"], street):     # value raise
    ...  return a pot-fraction raise
if to_call == 0:
    if street > 0 and eq < p["bluff_max_equity"] and random() < p["bluff_freq"]:
        return a bluff raise                                             # occasional bluff
    return check
pot_odds = to_call / (pot + to_call)
need = pot_odds + p["call_margin"] + p["bet_pressure"] * to_call / max(pot, 1)
if eq >= need: return call                                               # priced in
return fold

                  The bet_pressure term demands extra equity against big bets, because big bets usually mean strong hands: a crude stand-in for the range update. Simple, and surprisingly strong against weak opponents.

                  2.5.2 Tier 2: adaptation and the endgame lock

                  Tier 2 (bot/brains/tier2.py) keeps Tier 1's rule but adjusts its numbers to the opponent before each decision, each adjustment bounded:

                  • bluff more against players who fold to raises a lot, less against calling stations;
                  • against loose callers, value-raise with weaker hands and bet bigger;
                  • against players who raise almost always, shrink the "big bets are strong" penalty (their big bets mean little);
                  • on the turn and river, call less against a value-heavy bettor (low bluff index), more against an over-bluffer.

                  It also adds the endgame lock of Section 1.9.5. lock_margin (bot/situation.py:35) computes the lead minus the worst case of check-folding the rest of the match: what is already in the pot this hand, plus the blinds of every future hand with seats alternating. If positive, every decision is check/fold, and the match is mathematically won. (Since 31 October, a discard is still played normally while locked, because a discard costs no chips.)

                  2.5.3 Tier 3: the "Ivey" style

                  Tier 3 (bot/brains/tier3.py) is Tier 2 with a different betting policy, built from Chapter 1's equilibrium-flavoured ideas:

                  • Preflop: probability tables [fold, passive, raise] for four spots (button open, big blind against a limp, big blind against an open, button against a 3-bet), built from the 1,755-class equity table plus a "playability" score, with mixed (randomised) decisions near every cutoff.
                  • Flop and turn: continuation bets sized by board texture; facing a bet, defend by the minimum defence frequency of Section 1.5.5, ranked inside our own range; polarised turn barrels.
                  • River: value-bet the top third of our range, bluff at the bluff share that makes the opponent indifferent. Facing a river bet, Tier 3 uses Tier 2's bluff-catching rule, never MDF.
                  • Guards added after measurements: never fold a hand Tier 2's pot-odds rule would call (the eq_floor); give a postflop value raise to Tier 2 when Tier 2 would make one (the value_floor).

                  Every feature is a switch, so the lab can turn each one off and measure what it is worth (an ablation).

                  2.5.4 The discard

                  The discard (bot/sim/discard.py) is close to PIMC (Section 1.8.4). For each of the three possible discards, sample the opponent's hand (weighted by inference) and the remaining board, and estimate the showdown share of the two cards kept. Then keep the best. PIMC's flaws hardly matter here, because both discards are public anyway. A fast path skips the sampling when one option is clearly best.

                  2.6 The lab: how the bot is measured

                  • The engine (lab/engine.py) runs a match between two players. It uses the same rules code as the bot, plus an audit mode that checks chip conservation and that no player ever receives information it should not.
                  • The duplicate harness (lab/harness.py) plays every seed twice with seats swapped: duplicate pairs, as in the tournament (Section 1.3.2). Standard errors are computed per pair. Seeds run in parallel on all cores.
                  • The evaluator (lab/eval.py) plays a brain against a pool and prints chips/hand ± SE and match score per opponent. Its --compare mode is the project's acceptance rule (lab/eval.py:178): keep a change only if no opponent got worse by more than 2 SE, and the target (or the sum over opponents) improved, by more than 2 SE for a target. This is Section 1.10.5's guard 3. It also refuses to run against held-out opponents without an explicit --final flag.
                  • Opponents: five sparring bots (calling_station, tight, maniac, random_legal, all_in), the organisers' starter bot (lab/sparring/starter_bot.py, played over the real protocol), earlier tiers, and the nine-bot Discard Hold'em pool in Opps/discard/. Two are converted by hand from the team's LLM-written Hold'em bots (conv_opp3, conv_opp4). Seven were written from scratch by fresh AI sub-agents that saw only the rules, a one-paragraph prompt and a style brief (equity-vs-random, rule-based, loose-aggressive, trapper, exploiter, min-raiser, "theory" geometric). lab/opps/discard_pool.json splits them into six training bots and three held-out bots (d_conv_opp4, d_new_eqrandom, d_new_geometric).
                  • Resource checks: lab.timing_bench (time bank, projected to a 2× slower server) and lab.memory_check. Packaging: tools/package_submission.py builds the zip and re-runs every check on the unpacked copy.

                  2.7.1 The CFR attempt and why it stopped

                  Before the variant was known, the project built an external-sampling MCCFR with CFR+ updates (lab/cfr/mccfr.py; Sections 1.7.5 and 1.7.7) and tested it on plain Hold'em (reported, docs/reports/PHASE23.md):

                  • The solver is correct: on Leduc its exact exploitability fell steadily to 0.020 at 106 iterations (Section 1.7.8's check). A "trembling-hand" exploration setting without importance correction biased it: it stalled at 0.063 until removed. That is Section 1.3.1's rule that sampling without correction is biased.
                  • It was far too slow for the abstraction: about 68 iterations per second in pure Python on one core; 0.9 million infosets; after 2 hours, 75% of them had been visited fewer than 10 times.
                  • Every CFR strategy lost to Tier 2. The best full abstraction lost −0.29 ± 0.07 chips/hand (match score 0.375). Even a small, well-trained tree (30 big blinds deep, 4,300 infosets, median 155 visits each) lost −0.09 ± 0.02 (0.34).
                  • Causes, ranked: undertraining; abstraction quality (equity buckets from 64-sample estimates put ~38% of hands one bucket off; Tier 2's bet sizes needed translation in 3–11% of decisions); the exploration bias. These are Section 1.8.2's abstraction error and Section 1.7.4's convergence constant (proportional to the number of infosets) in practice.

                  The team decided CFR is a no-go for the shipped bot; the code stays in lab/ only. For this book, CFR remains an idea: Section 2.12 discusses where it could fit, with every figure labelled as an estimate.

                  2.8 New measurements: how every opponent plays

                  Measured for this book on 31 October 2026. Method: Tier 3 (the shipped brain, endgame lock off so that it keeps playing normally) played each opponent for 12 seeds × both seat orders = 24 matches of 400 hands, i.e. 9,600 hands per opponent and about 200,000 hands in total. Not one forfeit or illegal action occurred. From Tier 3's own record of each hand (Section 2.2) we extracted every opponent decision with its spot: street; whether they faced a bet or were checked to; preflop, whether they opened from the button, faced a raise, or faced a limp; and the action, with the raise size as a fraction of the pot. The analysis scripts are short and are kept outside the repository. Every number below is a frequency over thousands of decisions unless marked.

                  Two cautions from Chapter 1. First, these frequencies are measured against Tier 3's play: "folds 79% to our river bet" means against Tier 3's betting range and sizes. Bots that fold by their own hand strength will fold similarly to any bettor; bots that read bet size will not. Second, "shown river bets weak" counts only bets that reached showdown, and bluffs that we folded to are never shown, so it underestimates bluffing (Section 2.4.4).

                  Column guide: VPIP = how often they put chips in voluntarily preflop; PFR = how often they raise preflop; folds to our bet = their fold rate facing a Tier 3 bet or raise on that street; bets river when checked to; shown river bets weak = of their river bets that reached showdown, the share made with a hand below the median of all possible hands on that board; WTSD = went to showdown, among hands where they saw the flop; discards lowest = at showdown, their discard was the lowest of their three cards.                   2.8.1 Reading the table: four families

                  The table sorts into a few families with very different weaknesses, which is exactly what a type library needs (Section 1.9.1).

                  1. Over-folders: d_new_exploiter (folds 65% / 79% / 79% to our flop / turn / river bets), d_conv_opp3 (42% / 68% / 72%), d_new_rules (62% / 59% / 59%) and d_new_geometric (55% / 41% / 56%). By Section 1.5.4, a pot-sized bluff with zero equity needs only 50% folds, a half-pot bluff 33%. Against a 79% folder a pot-sized bluff earns 0.79·P − 0.21·P = +0.58 pots every time. Tier 3 loses chips to all four.
                  2. Value-only bettors: when d_new_exploiter, d_new_rules, d_new_minraise, d_new_eqrandom, d_new_geometric or d_new_trapper bet the river and show down, the hand is weak 0–6% of the time. Even allowing for the bias, their river bets are overwhelmingly value. By Section 1.5.5, facing a pot-sized bet a bluff-catcher needs 33% bluffs to call: against these bots, calling with a bluff-catcher is simply throwing chips away. This is the river leak of Section 2.7, now explained per bot.
                  3. Stations: the organisers' starter and calling_station never raise and call everything (WTSD 100%). d_new_trapper is a softer version: it rarely raises preflop (PFR 3%), folds only 21–32% to our bets, and when it does raise a river bet (22% of the time), it means strength. Against stations: no bluffs, value-bet thinner and bigger.
                  4. Aggressors: d_new_lag (VPIP 90%, PFR 59%, bets the river 66% of the time when checked to, folds rarely) and maniac. Tier 3 already beats them (+5.8 and +49 chips/hand): its "never fold a priced hand" guard (Section 2.5.3) works.

                  The rest sit in between: d_new_eqrandom, d_new_minraise and d_conv_opp4 fold 40–52% to later-street bets and bluff rarely; d_conv_opp4 and d_new_geometric also fold about half their hands to a preflop raise. The discard column separates the LLM bots (they throw their lowest card 60–68% of the time, a sensible keep-the-best-two habit) from the sparring bots (about 36%, close to random) and the starter (100%, the rules' fallback). A discard reveals something at every flop, so this is cheap evidence for identification.

                  Key finding

                  The pool's typical LLM-written bot folds too much to bets and almost never bluffs the river. The best response to that is the opposite of what Tier 3 does on the river: bet and bluff more, call less. Tier 3's adaptation cannot get there by design. Its per-spot statistics may move play only after 20 observations and by at most 15 percentage points, and bluffing scales up to only 2× its base rate (Section 2.4.4). That is a deliberate brake against noise, and also exactly what prevents exploiting a 79% folder. The exploit layer exists to lift that brake once the evidence is strong.

                  2.8.2 The original Hold'em bots

                  The team's four LLM-written Hold'em bots (Opps/opp1–opp4) cannot play Discard Hold'em, so they were profiled the same way on plain Hold'em with 200-chip stacks, against Tier 2 (Tier 3 is specific to three-card hands). They are the ancestors of d_conv_opp3 and d_conv_opp4, and a sample of what LLMs write when asked for a poker bot.

                  The same two habits appear in the ancestors. opp3 and opp4 are over-folders (52–78% folds to later-street bets; the SPRT says "yes" in 24/24 and 22/24 matches, after about 80 hands). Yet opp3 beats Tier 2 in 22 of 24 matches (−2.10 chips/hand): the same failure to exploit folding as in Discard Hold'em. opp1 and opp2 never showed a weak hand after betting the river (0% in 9,600 hands each). When LLMs write poker bots, these two habits look like the default, not a coincidence of one prompt.

                  2.9 Catching a bot: how fast can we tell?

                  Two measurements on the same recorded matches, both measured.

                  Identity (Section 1.4.3): a naive Bayes classifier over the 17 known opponents. Its features are the opponent's (street, spot, action) symbols, with probabilities per spot and Laplace smoothing. It was trained on seeds 0–5 and tested hand by hand on the unseen seeds 6–11. We record the hand at which the true bot's posterior first reaches 95%, and whether the top guess is right after 50, 100 and 400 hands.

                  Traits (Section 1.4.2): two SPRTs with α = β = 0.05, needing no training at all. "Over-folder": the fold rate facing our postflop bets is 0.6 rather than 0.4. "Station": the rate of continuing (call or raise) facing our river bets is 0.8 rather than 0.5. Each cell gives how many of the 24 matches ended with a "yes" or "no" verdict, and the median hand at which the test stopped.

                  What the numbers say:

                  • Among known bots, identity is caught almost immediately: within 2–20 hands for 13 of the 17, and correct after 50 hands for all of these. Two pairs are the exceptions, and both are instructive. The starter and calling_station bet identically (they only differ in discards, which the classifier did not use). And tier1 and tier2 share most of their code. In both cases the right exploit is the same for either member of the pair, so the confusion costs nothing.
                  • The closed-set result is optimistic. Real opponents are not in our library. A real bot will be classified as its nearest known neighbour, confidently and possibly wrongly: the over-confidence of naive Bayes from Section 1.4.3. Identity is therefore a hint, never a licence.
                  • Traits are the robust signal, and fast enough. The over-folder test says "yes" in 24/24 matches against d_new_exploiter (median 37 hands), 22/24 against d_new_rules (40 hands), 24/24 against d_conv_opp3 (108 hands), and 15/24 against d_new_geometric (84 hands). It says "no" against every station and aggressor. Stations are flagged in about 18 hands. That is well inside a 400-hand match.
                  • The river-bluff trait is too slow to measure directly. It needs showdowns of river bets. Against d_new_exploiter only 364 such showdowns happened in 9,600 hands, one every 26 hands, so the 20 observations Tier 2's gate requires take about 500 hands: longer than a Stage-1 match. This is Section 1.4.2's lesson in the flesh: detection speed is limited by how often the informative event occurs.
                  Key idea: catch fast traits, infer slow ones

                  The fast trait (over-folding, about 40 hands) and the slow trait (never bluffing the river, about 500 hands) go together in this pool: every over-folder is also a value-only river bettor. A type library turns the fast observation into a belief about the slow one. That is the real reason "catching the bot" is worth so much: once we know what kind of bot it is, we know things about it that the match is too short to measure.

                  2.10 Designing the exploit layer

                  This section is a design built from Sections 1.4 and 1.9 and the measurements above. It is not implemented. Both designs of Section 2.12 plug into it, and the improvement loop of Section 2.11 tunes its numbers.

                  2.10.1 Architecture

                  1. Evidence. Every opponent decision as a (street, spot, action, size) symbol, every discard (lowest or not), every showdown (hand percentile against the line taken). The Tier 2 machinery already collects most of this (Section 2.4.4).
                  2. Trait tests. One SPRT per exploitable trait (Section 1.4.2): over-folder, station, river bluffer, preflop over-folder, raise-means-nuts. Each also keeps a shrunk rate estimate (Section 1.4.1) so that the size of a deviation, not only its existence, is known.
                  3. Type posterior. A naive Bayes posterior over a library of styles built from Table 2.2, plus an explicit "unknown" class with broad, population-average probabilities, so that a novel bot can be recognised as novel. Types carry the slow traits (river bluffing) that the match cannot measure (Section 2.9).
                  4. Confidence λ per counter-move (Section 1.9.4). λ = 0 below a minimum evidence level, rising to 1 as the relevant SPRT crosses its boundary and the type posterior agrees. Counter-moves that are cheap when wrong (folding a bluff-catcher to a bot that bluffs a little) get λ early; costly ones (bluffing every river) need strong evidence.
                  5. Adjustments to the base policy, scaled by λ (Section 2.10.2).
                  6. Bail-out monitor (Section 1.9.3). A CUSUM on the gap between predicted and observed fold rates, and on results: if a flagged over-folder starts calling our bluffs, drop λ to 0 for that move. This matters especially because d_new_exploiter is itself an adaptive exploiter and may change gear.
                  7. P(win) control (Section 1.9.5). Late in a match with a lead, shrink variance (smaller bluffs, fewer marginal all-ins); the endgame lock remains the final word.

                  2.10.3 Where it plugs in

                  For Design C or B the layer is a policy wrapper around Tier 3, in the same pattern as Tier 2's adjusted parameter copy (bot/brains/tier2.py): before each decision, compute λ for each counter-move and produce adjusted parameters (bluff frequency, value thresholds, call margin on the river, bet sizes). The structural change is that the caps become functions of λ: today's ±15 points at λ = 0, wider as evidence grows. For Design A the same adjustments apply to the blueprint's action probabilities, RNR-style (Section 1.9.2).

                  2.10.4 How to test it

                  • Detection tests, deterministic, on recorded matches like those of Section 2.9: each trait test must say "yes" for the bots in its row and "no" for the others, within a hand budget.
                  • Counter-move tests at the policy seam: given a confident over-folder posterior, a weak hand that is checked to bets; given a value-only bettor, a bluff-catcher folds to a river bet.
                  • Acceptance with the unchanged rule (lab/eval.py --compare) against the training pool, then fresh seeds. And, because the held-out bots' patterns are now known, a new held-out set (Section 2.11).
                  • Adversarial check: a lab bot that plays like an over-folder for 100 hands and then calls everything. The bail-out must catch it before it costs more than a set limit.

                  2.10.5 Playing for the match, not the chips

                  With μ and σ as in Section 1.9.5, the exploit layer's value is in raising μ against the bots where it is negative today. Against the over-folders, moving μ from about −1 to about +2 chips/hand turns P(win) over 400 hands from roughly Φ(−0.4) ≈ 0.34 to Φ(0.8) ≈ 0.79 (estimate, σ = 50). Margins beyond the tie-break cap (400 chips per Stage-1 match, 1,000 in Stage 2) are worth nothing, so once a match is safely won, the controller should spend no more variance.

                  2.10.6 A bug found while measuring: Tier 3 can silently become Tier 2

                  Measured: during the profiling runs (four matches in parallel on four cores), Tier 3 logged tier3 _bets failed: AssertionError() 595 times, together with a handful of hard-deadline hits. The cause, reproduced: _preflop_model() in bot/brains/tier3.py builds its preflop model and assigns it to self._model, then builds the own-range helper self._own. If the hard deadline fires in between (it raises DeadlineExceeded, which by design escapes ordinary exception handlers), the model is set but _own stays None. The model is never rebuilt, so every later postflop decision hits assert … self._own is not None and falls back to Tier 2. One deadline at that moment disabled Tier 3's postflop play for a whole 200-hand test match (597 fallbacks). On the real server, which may be twice as slow, the first decision is the most likely to hit the deadline. The fix is to build both objects into local variables and assign them together (or to build them before the first request, outside the time bank). It is a few lines in the submitted bot, so it is listed as a decision in Section 2.13.

                  2.11 A self-improving loop: Claude's proposal

                  Proposal

                  This section and the next are a proposal for you to argue with, not a decision. They use Chapter 1's tools and this chapter's measurements. Where a number is not measured it says estimate.

                  Your instinct, "face a slightly better bot and keep learning", is right in spirit. Section 1.10 explains why it needs a population and a gate. Here is the concrete version for this repository.

                  2.11.1 What evolves, and what it is scored on

                  • The genome is a parameter vector θ: Tier 3's numbers (in bot/config/tier2.json and tier3.DEFAULTS) plus the exploit layer's numbers (Section 2.10: type-detection thresholds, per-type adjustments, the confidence schedule λ). It is not new code. Code changes stay a human (or session) decision; the loop tunes them once they exist.
                  • The score is match points, i.e. P(win) of Section 1.9.5, measured as match score over duplicate pairs with the lock on, as shipped. Chips/hand ± SE is the tie-breaking secondary metric, because it has lower variance.

                  2.11.2 The league

                  • Champion: the current best θ.
                  • Frozen past champions: every promoted θ stays in the pool, so a cycle back to an old weakness shows up as a regression (Section 1.10.2).
                  • External opponents: the six training bots, the starter, the sparring bots, Tier 2. They anchor the league to bots the champion did not create, which is the defence against self-play drift.
                  • Exploiters: a separate search for θx that beats the current champion (AlphaStar's main exploiter, Section 1.10.3). An exploiter that wins exposes a hole; it then joins the league as an opponent, and the next champion must cope with it.
                  • Fresh blood: every few generations, generate two or three new LLM-written bots with the Phase F prompt. Some join the training pool; at least two form a new held-out set, replacing the one whose patterns were read for this book.

                  2.11.3 One generation

                  1. Propose 16 candidates: mutations of the champion, with one or two parameters changed each (CMA-ES or simple Gaussian steps; Section 1.10.5).
                  2. Screen with successive halving: 4 pairs against every league member; keep the top 4; 16 more pairs; keep the top 1–2.
                  3. Gate the finalist with the repository's unchanged acceptance rule (lab/eval.py --compare: no opponent worse by more than 2 SE, sum improved), on 50 fresh-seed pairs. Also require: a head-to-head match score against the champion above 0.5 by 2 SE; the full test suite green; time bank ≤ 50% projected at 2× slower; memory under the limit.
                  4. Promote or reject; append the result to a ledger (one JSON line per candidate: θ, seeds, every number). Rollback is "use the previous ledger line".
                  5. Exploiter step: a short search for θx against the new champion; if one wins by 2 SE, add it to the league.

                  Overfitting to Claude-written bots: seven of the nine pool bots come from one model family, so the loop could learn to beat "AI-written poker" in a way real teams' bots do not share. Selection bias: 16 candidates per generation is exactly the multiple-testing setting of Section 1.2.3, hence the fresh-seed gate. Compute: two weeks is about 100–140 generations at most on one machine (estimate). That is enough to tune dozens of parameters, not to discover new strategy.

                  2.12 Two designs for the last two weeks: A and B

                  You asked for both, side by side, without a pick. Both share the exploit layer (Section 2.10) and the loop (Section 2.11). CFR appears here only as an idea; nothing in this section has been built or measured for Discard Hold'em.

                  2.12.1 Design A: a CFR blueprint with the exploit layer on top

                  Idea. Replace Tier 3's hand-written betting policy by an equilibrium approximation (a blueprint, Section 1.8.3), trained offline with CFR+ or MCCFR, possibly on your GPU. Then let the exploit layer deviate from it, RNR-style (Section 1.9.2), once an opponent type is caught. The appeal: the base is unexploitable by construction, so the exploit layer starts from a fortress; and good regrets are a principled place to inject exploitation.

                  What it needs.

                  1. An abstraction of Discard Hold'em: the 1,755 lossless preflop classes; flop buckets for three-card hands; the discard decision (a simultaneous move with private information, best modelled as sequential with the second discard hidden); turn and river buckets; 2–3 bet sizes plus all-in; action translation.
                  2. A fast trainer: the vector form of Section 1.7.6 with public chance sampling, which updates every private hand per iteration. This is the "Phase 25" the repository judged necessary and never built. On a GPU the range-vector operations batch well.
                  3. An exporter that fits the strategy into the 5 MB submission (one byte per infoset-action, estimate: up to about 2–4 million entries after compression), and a runtime that looks up buckets within the time bank.
                  4. An RNR-style exploit hook: per opponent type, either a precomputed restricted response or a bounded shift of the blueprint's action probabilities.

                  Evidence for and against (reported): the repository's MCCFR is correct (Leduc) but lost to Tier 2 with every Hold'em abstraction, including a small well-trained one (Section 2.7.1). Causes were undertraining and abstraction quality, both of which a vectorised GPU trainer and a better abstraction address in principle. Discard Hold'em is bigger than Hold'em per hand, but its preflop is cheaper to make lossless.

                  First test, before committing to it (the repository's own "cheap proof first"): within 3–4 days, a blueprint with the exploit layer off must at least match Tier 3 head-to-head (match score ≥ 0.5 within 2 SE over 100 pairs) and not be worse than Tier 3 against the training pool. If it fails, stop and fall back to B or C.

                  2.12.2 Design B: Tier 3 plus a river solver, with the exploit layer

                  Idea. Keep Tier 3 for preflop, flop and turn, where it already beats Tier 2 and the simple bots. Replace only its weakest decision, river play, by a small equilibrium computation: at each river decision, solve the river subgame with vector CFR+ (Section 1.7.6; 903 hands per player). Use entry ranges from the existing inference (Section 2.4.3), adjusted by the exploit layer's opponent type (a type that never bluffs gives a value-heavy betting range). This is unsafe subgame solving (Section 1.8.3) with a model-based range. It directly attacks the measured leak, river showdowns against value-heavy bettors (Section 2.7).

                  What it needs. A river tree (2–3 bet sizes plus all-in, 2 raises); a showdown using the sort trick (Section 1.7.6); a time-bounded solve with a fallback to Tier 2's rule; tests against a small game with known value.

                  The binding constraint is time, not memory (estimate). The bank is 60 s per 400 hands, so about 150 ms per hand, and the bot uses about a quarter of it today. A river decision happens in perhaps a third of hands. If one CFR+ iteration over a 903-hand river costs about 1 ms with O(n) showdowns, a 50–150-iteration solve costs 50–150 ms. That is affordable only with care: cap iterations by the budget, solve once per river and reuse the solution across our river decisions, and fall back when time is short. With O(n2) showdowns it is 5–10× slower and does not fit.

                  First test: within 2–3 days, the river solver must improve chips/hand against the training pool by more than 2 SE under the acceptance rule, with no opponent worse, and stay within the time bank at 2× slower.
